## 2. Authentication & user management (P0 — decided, "très similaire à Supplier Portal")

Decided 2026-08-24 in Cowork. Full spec, roles, and flow diagram in `CLAUDE-CONCEPT.md` section 4. Two-role model (`ADMIN`/`USER`) plus a `PENDING` gate — simpler than Supplier Connect's brand/supplier split since this tool has no such distinction.

- [x] **BL-019** — Done 2026-08-25: `User` model + standard NextAuth tables (`Account`, `Session`, `VerificationToken`) via `@auth/prisma-adapter`; `Role` enum (`ADMIN`/`USER`/`PENDING`). `prisma/schema.prisma`.
- [x] **BL-020** — Done 2026-08-25: NextAuth v4 setup, `GoogleProvider` only, `lib/auth.ts` mirroring Supplier Connect's structure.
- [x] **BL-021** — Done 2026-08-25, with one deviation from the original plan: the domain/bootstrap-admin role resolution runs in the **`jwt` callback**, not `signIn` — the Prisma adapter only persists a brand-new user *after* `signIn` resolves, so resolving the role inside `signIn` would race the adapter's own `createUser()`. The `jwt` callback resolves it right after the row is guaranteed to exist, only ever moves a user *out of* `PENDING` (never overwrites an admin-assigned role), and re-reads the DB on every request — which is also what makes an admin's Validate/role-change take effect without the user re-logging in.

Verified live: saves and reloads correctly, and saving tenant URL/API key alone still works unchanged.
- [x] **BL-041** — Done 2026-08-28: `LocationMapCard`'s map fetch falls back to the legacy floor-plan endpoint when `location-api-v2` returns `403` specifically (not 401/network/404, which keep their existing handling) and Basic Auth credentials are configured; otherwise the original error is returned with a hint to add credentials in Settings. **Two corrections found during the required live check, before wiring anything in** (see `CLAUDE-CONCEPT.md` section 7.4 for full detail):
  - The floor-matching rule in the original spec (match the floor whose `name` equals the site's `name`) **never holds** — checked against all 3 seeded sites, a floor's `name` always mirrors its own `code` (e.g. `TTMEMBASE_FLORR`'s name is `TTMEMBASE`), never the premise's display name (`T&TMembase`). The real, reliable link is structural: a floor's `parent` field holds its premise's numeric `id`. Implemented as `findFloorForPremiseCode()` (supersedes the originally-planned `findFloorByName()`).
  - The `/maps` endpoint returns **raw image bytes** (`Content-Type: image/png`, confirmed against a real 5718×3457 floor plan), not JSON metadata with a URL as first assumed. Since the browser can't hold the Basic Auth credentials, added a new streaming route `GET /api/locations/[code]/legacy-map-image` that fetches server-side and proxies the bytes; `LocationMapCard`'s `<img src>` points there. `LocationMap.width`/`height` made optional — the fallback path omits them, so the `<img>` renders at its natural pixel size, which is actually required for the zone/device marker overlay (positioned in raw pixel coordinates) to line up correctly.
  - Live-verified end-to-end in the browser against `TTMEMBASE`: the map card renders the real floor plan with zone/device markers correctly positioned, where it previously showed the `403` error state.
