# Bartender Track and Trace Simulator — Product Specification

> Working document. Skeleton drafted in Cowork on 2026-08-24, from the project brief and Luc's background running the Bartender Track & Trace platform. Much is still to be settled — see section 12. Product name decided 2026-08-24: **Bartender Track and Trace Simulator** (repo `collector-simulator` remains the technical identifier — see `CHARTE-GRAPHIQUE.md`, `BACKLOG.md` BL-000).

## 1. Pitch

A web app that simulates real-life Track & Trace infrastructure — the devices, workflows, and serialized items that normally exist on a factory floor, packaging line, or distribution site — so that realistic, controllable data can be produced against the **Bartender Track & Trace platform** without needing physical hardware. It lets its users spin up virtual Devices, define Workflows for them to run, and generate new Serialized Items (with or without a physical label) that flow through those workflows and get reported to Bartender via its APIs.

## 2. Concept

Three pillars, per the initial brief:

1. **Devices** — simulate the pieces of real-life infrastructure that produce Track & Trace events in an actual deployment (e.g. RFID readers/printers, barcode scanners, encoding stations, gateways). Each simulated device stands in for a physical one and can be configured, started, and stopped independently. *Device types, configuration fields, and behavior model still to be detailed — see section 11.*
2. **Workflows** — the sequence of steps a serialized item goes through (e.g. encode → verify → pack → ship), and which device(s) perform each step. A workflow is what turns a set of devices into a coherent simulated process. *Workflow structure, step types, and how workflows attach to devices still to be detailed.*
3. **Serialized Items** — create new serialized items (individual unit/case/pallet identity — e.g. a GTIN + serial, an EPC, or similar) **with or without a label**: some items get a simulated physical label/tag printed and encoded as part of the workflow, others are tracked as "born digital" identities with no physical label. *Identity scheme, label format(s), and the with/without-label distinction still to be detailed.*

## 3. Bug reporting (built now — P0)

Built from day one, not deferred — mirrors ChefMate's mechanism exactly (Luc: "really useful"), translated to this project's stack.

- **Model**: a `BugReport` record per report — a short `number` (human ref, autoincrement, distinct from the cuid `id`), title, description, reporter, status (`OPEN` / `RESOLVED`), optional `screenshotUrl` (Cloudinary), timestamps (reported, resolved), plus operational `notifiedStartAt` / `notifiedResolvedAt` (BL-010, keep the notify scripts re-runnable — never shown in the UI).
- **Reporting**: "Report a bug" in the avatar menu (decided 2026-08-24, see section 4's navigation note) opens the form as a modal, from anywhere in the app — captures title, description, and an optional screenshot, without navigating away from the current screen.
- **`BUGS.md`**: a snapshot of all currently `OPEN` bugs, regenerated on demand via `npm run bugs:export` — not continuously synced, so it can be stale between runs. Read it fresh before starting bug work.
- **`SOLVED-BUGS.md`**: append-only archive of resolved bugs (number, title, description, dates, screenshot URL if present), written to when a bug is marked `RESOLVED`.
- **Scripts** (BL-009/010/011, built 2026-08-31, `scripts/*.ts` via `tsx`, all against `DATABASE_URL_PRODUCTION`, `<ref>` = `number` or cuid `id`): `bugs:export` rewrites `BUGS.md`; `bugs:notify-start -- <ref>` emails the reporter that work started; `bugs:resolve -- <ref>` marks `RESOLVED` + archives to `SOLVED-BUGS.md` + regenerates `BUGS.md`; `bugs:notify-resolved -- <ref>` emails that the fix is live, then deletes the row. Email is Resend (`lib/email.ts`); with no `RESEND_API_KEY` the DB side still runs and the email is skipped. `notifiedStartAt`/`notifiedResolvedAt` guard against double-emailing on a re-run.
- **Environment targeting**: once staging/production environments exist, all of the above targets the production database specifically (`DATABASE_URL_PRODUCTION`) — bug reports only ever come from the live app, same reasoning as ChefMate.
- Full step-by-step process lives in `CLAUDE.md`, "Bug handling".

## 4. Authentication & user management (built now — P0)

Built from day one, not deferred — mirrors Supplier Connect's mechanism (Luc: "très similaire à Supplier Portal"), simplified to a two-role model since this app has no brand/supplier split.

**Roles**: `ADMIN` (full access, including Settings → Users), `USER` (everyone else — nearly all users), `PENDING` (signed in once, waiting on an admin).

**Sign-in**: Google SSO only (NextAuth v4 + `@auth/prisma-adapter` + `GoogleProvider`, same libraries as Supplier Connect's `lib/auth.ts`). No email/password login for this internal tool unless a need for it shows up later.

**Auto-approval rule (new — not present in Supplier Connect today)**: on first sign-in, if the Google account's email domain is in an `AUTO_APPROVED_SSO_DOMAINS` allowlist (starts with just `seagullsoftware.com`), the user is created directly as `USER` — no waiting. Every other domain creates the user as `PENDING` and sends them to a waiting page (`/auth/pending`, polling an auth-status endpoint every 30s, same pattern as Supplier Connect's `PendingPage.tsx`) until an admin validates them from Settings → Users.

**Bootstrap problem**: since nobody starts as `ADMIN`, an `INITIAL_ADMIN_EMAILS` env var lists email(s) — Luc's — that get `ADMIN` directly on first sign-in, bypassing both the domain check and the `PENDING` state. Without this there'd be no way to ever reach the Users tab that grants admin in the first place.

**Safety rule (new, not in Supplier Connect)**: the last remaining `ADMIN` can't be deleted or demoted to `USER`, by anyone, including themselves — prevents an accidental full lockout with nobody able to manage users.

**Settings**: a `/settings` area accessible to every signed-in user, tabbed. The first tab, **Users**, only renders for `ADMIN` (hidden entirely for `USER`, not just disabled/greyed out — mirrors Supplier Connect's `isBrandAdmin` gate, both server-side on the API routes and client-side on the tab list). The second tab, **Bartender Connection** (added 2026-08-27, see section 7.1 below), is open to **every** role including `PENDING` — deliberately not admin-gated, since each user configures their own connection rather than a shared org-wide one.

**Users tab** (admin-only): a table of all users — name/email, avatar, role, joined date, **last active** (BL-087, added 2026-09-14 — see below). Three actions, exactly what Luc asked for:
- **Validate** — for a `PENDING` user, assigns them a role (default `USER`, admin can pick `ADMIN` directly) and lets them in.
- **Change role** — inline role switch (`ADMIN` ⇄ `USER`) for any already-validated user, blocked by the last-admin safety rule above.
- **Delete** — permanently removes a user, with a confirmation prompt, also blocked by the last-admin rule.

No suspend action for now (Supplier Connect has one; not part of what was asked — delete covers it for this tool, suspend can be added later if a softer removal is ever needed).

**Inspired-by addition (from Supplier Connect's `AdminNotification` system, scoped down)**: a small pending-count badge, shown on the Users tab itself (see navigation below).

**Navigation (decided 2026-08-24, revised 2026-08-30)**: desktop layout only for now — left sidebar for the main app sections: **Overview, Devices, Workflows** only. **Serialized Items removed 2026-08-30** — the Item Feed entity (section 16) absorbs that concept entirely (a Feed's `FIXED` kind, and what `NEW` mints, are the only "serialized items" this app ever touches), so a separate nav entry no longer makes sense per Luc's explicit request. Bug Reports is deliberately **not** in the sidebar (revised 2026-08-24: it's a help/improvement channel, not a core function of the tool, so it doesn't earn a top-level slot) and neither is Settings — both live **only** behind the user avatar in the top-right corner of the top bar. Click it to open a small menu: name/email/role, then **Settings**, then **Report a bug**, then Sign out. Settings itself (including the admin-only Users tab) opens as its own view once "Settings" is clicked there; "Report a bug" instead opens the bug-report form (see section 3) directly as a modal, without leaving the current screen — reporting a bug shouldn't require navigating away from whatever you were doing when you hit it. This is a deliberate difference from Supplier Connect, where Users is a top-level sidebar item — here both Settings and bug reporting are nested one level deeper, being either admin-only or secondary to the app's core purpose. Mobile/tablet layout not addressed yet (see `BACKLOG.md` BL-028). First mockup: `mockup-app-shell.html` (published as a Cowork Artifact) — interactive, shows the sidebar, the avatar menu opening, the bug-report modal, and the Users tab with a live pending → validate flow.

**Flow**:

## 7. Bartender Track & Trace API integration

The simulator's output (device events, workflow executions, serialized item creation/movement) is reported to the **Bartender Track & Trace platform** via its APIs. Luc will provide the relevant API specs **incrementally, one at a time**, as each integration point becomes needed — this section grows as each API is documented.

**First real API provided 2026-08-27** — see 7.1/7.2 below. Everything else is still incremental, one API at a time, as Luc provides it.

### 7.1 Per-user connection settings (prerequisite for all Bartender calls)

**Decided 2026-08-27.** Every call this simulator makes to the Bartender Track & Trace platform is authenticated per-user, not per-org: each signed-in user — **any role, including `PENDING`**, not just `ADMIN` — configures their own connection in **Settings → Bartender Connection** (see section 4):

- **Tenant URL** — the base URL of the user's Bartender tenant, e.g. `https://demotrackandtrace.sandbox.bartender-tt.com`. Different users may point at different tenants (sandbox vs. a client's tenant, different demo environments) — this is why it's per-user rather than a single app-wide setting.
- **API key** — sent as the `apikey` request header on every call to that tenant (see 7.2 for a confirmed working example). **Stored encrypted at rest** (AES-256-GCM, server-side `ENCRYPTION_KEY`) — decided 2026-08-27 given this key grants real access to a Bartender tenant. The UI never re-displays the plaintext key after saving; it shows only the last 4 characters, and the user must re-enter the full key to change it.
- **Test connection**: Settings offers a "Test connection" action that calls the Locations API (7.2) server-side with the entered (or already-saved) credentials and reports success (with a location count) or a clear error — this is the mechanism a user uses to confirm their tenant URL + key actually work, and doubles as the first live proof this integration works end to end.

Data model: two new fields on `User` (`bartenderTenantUrl`, `bartenderApiKeyCiphertext`) plus a `bartenderApiKeyLast4` convenience field for masked display — see `BACKLOG.md` BL-032.

### 7.2 Locations (sites) API

**Provided by Luc 2026-08-27** — the first concrete Bartender endpoint, and the one used to implement "Test connection" above.

- **Purpose**: returns the locations (sites) configured for the calling tenant.
- **Method / path**: `GET {tenantUrl}/statemachine-api-configuration/rest/configuration/locations?level=premise`
- **Auth**: header `apikey: <the user's API key>` (not `Authorization: Bearer` — a plain custom header named `apikey`).
- **Confirmed working example** (Luc's sandbox tenant):
  ```
  curl --location 'https://demotrackandtrace.sandbox.bartender-tt.com/statemachine-api-configuration/rest/configuration/locations?level=premise' \
  --header 'apikey: XCONEBOUVGDPDIOD'
  ```
- **Response shape** — **confirmed 2026-08-27** against the sandbox tenant (33 locations returned): a **plain JSON array** of location objects (not wrapped in `{ data: [...] }` or similar), each shaped like:
  ```json
  {
    "id": 59414424685263,
    "code": "TTMEMBASE",
    "name": "T&TMembase",
    "level": "premise",
    "type": "dc",
    "latitude": 35.06612,
    "longitude": -89.955986,
    "sgln": null,
    "bizLocation": "urn:mjx:site:loc:DEMOTT.00005.0",
    "bizLocationRegularizer": "urn:mjx:site:loc:DEMOTT.00005.0",
    "hotspotZOffset": 0,
    "attributes": "asn_auto_on,inventory_app_flow_transferout_receiving",
    "addressLine1": "", "addressLine2": null, "addressLine3": null,
    "addressPostalCode": "", "addressCity": "Memphis", "addressState": "TN", "addressCountry": "USA",
    "hierarchy": { "organizationId": 1000, "premiseId": null, "floorId": null, "areaId": null, "zoneId": null },
    "parent": 1000
  }
  ```
  `type` seen so far: `dc`, `store`, `factory`, `customer` — likely an open set, not a fixed enum. `attributes` is a comma-separated string or `null`, not an array. `id`/`parent` are numbers (large enough that they don't fit a 32-bit int). Only used today for a location **count** ("Test connection" — BL-033); if a `Location`/`Site` concept is ever needed for BL-003, model against this shape directly rather than re-deriving it.
- **Error behavior** — confirmed against the same sandbox tenant: an invalid `apikey` returns **HTTP 401** with a plain-text body `Unauthorized` (not JSON). A malformed/unreachable tenant URL fails at the network level (DNS/connection error) before any HTTP status is returned — handle both distinctly rather than a single generic "failed" message (see `app/api/settings/bartender/test/route.ts`).
- **Other query levels**: the `level=premise` parameter implies other levels likely exist (e.g. a site hierarchy) — not explored yet, out of scope until needed.

### 7.3 Location/Zone management API (`location-api-v2`) — provided 2026-08-27, gateway/auth corrected and confirmed working same day

A second, much more complete Location-related API spec, added directly to the claude.ai Project as `location-api-v2 (1).yaml`. Full CRUD for **Locations** (sites), **Zones** (named points on a Location's floor plan, each carrying a business purpose via `ZoneType`), **Location Types**/**Zone Types** (read-only reference/classification data), floor-plan image upload/retrieval, **Channel Mappings** (links one of Bartender's own registered `DataCollector` Channels to a Zone — **not** the same thing as this app's own simulated `Device` concept, see section 14.2), and CSV bulk import/export.

**Gateway architecture**: unlike the `statemachine-api-configuration` endpoint (section 7.2), which is reached at the user's own per-tenant subdomain (`{tenantUrl}/...`), `location-api-v2` (and the platform's `DataCollector` API, not yet documented here) are reached through **one of two fixed API gateways**, not the tenant URL directly:

- **Production gateway**: `https://api.bartender-tt.com`
- **Sandbox gateway**: `https://api.sandbox.bartender-tt.com` — **corrected 2026-08-27**; Luc's first pass called this the "staging" gateway at `api.staging.bartender-tt.com` (that host doesn't work — see the dead end noted below), the real second gateway is for **sandbox** environments.

**Which gateway to call is derived from the user's stored `bartenderTenantUrl`** (not stored separately): if it contains `sandbox` (e.g. `https://demotrackandtrace.sandbox.bartender-tt.com`, the tenant used for every live test in this section), use the sandbox gateway; otherwise use the production gateway. Implemented as `resolveGatewayUrl(tenantUrl): string` in `lib/bartenderLocations.ts`.

**Auth**: the **lowercase `apikey` header** — same header as section 7.2's `statemachine-api-configuration` endpoint, **not** `X-API-Key` as the original spec text implied. Confirmed 2026-08-27 by live-testing both header names against both gateways with the sandbox tenant's key (`XCONEBOUVGDPDIOD`, confirmed working for section 7.2):

- `https://api.staging.bartender-tt.com/locations` (the old, wrong gateway guess) — unreachable regardless of header: TLS handshake stalls after the server sends its certificate, no response ever comes back. Infrastructure/cert issue on that host, or simply not a real endpoint — moot now that the correct host is known.
- `https://api.bartender-tt.com/locations` (production gateway, wrong for a sandbox tenant) — `401` with either header. Expected: a sandbox key isn't valid on the production gateway.
- `https://api.sandbox.bartender-tt.com/locations` with `X-API-Key` — `401`, `{"message":"apikey or basic auth is required"}` (header not recognized).
- `https://api.sandbox.bartender-tt.com/locations` with `apikey` (lowercase) — **`200`, 33 locations returned.** This is the working combination.

Key points relevant to this app, confirmed against the live response shapes (not just the spec text):
- `GET /locations` — returns a **paginated envelope**, `{ page, total, pageSize, locations: [...] }`, not a bare array. Each location has `code`, `name`, `type` (`DC`/`FACTORY`/`STORE`/`SUPPLIER`/`CUSTOMER`), `address`/`zipcode`/`city`/`state`/`country`, `lat`/`lng`, `hasMap` (boolean), `zoneCount`, plus some fields this app doesn't use (`sgln`, `bizLocation`, `createdAt`/`updatedAt`).
- `GET /locations/{code}/zones` — returns `{ locationCode, zones: [...] }`. Each zone's own identity is under `zoneCode`/`zoneName` — confusingly, `code`/`name` on the same entry are the **parent location's**, repeated on every zone. Each zone has a `position` (`{x, y}` pixel coordinates on the floor-plan image) and a `type` (nullable) driving default EPCIS semantics. Live-tested against `TTMEMBASE` — 200, real zone data.
- `GET /locations/{code}/map` — floor-plan image metadata (`mapUrl`, `width`, `height`) when `hasMap` is true. Live-tested against `TTMEMBASE` (`hasMap: true`) — returned **`403`, plain-text `Access Denied. Not Authorized to use the resources: Local Map[read]`**, a permission-scope gap on this specific key, distinct from the already-handled `404` "no map for this location type" case. Not something this app can fix; the client surfaces it as a normal gateway error rather than silently treating it as "no map".

**Implication for BL-036–039**: `lib/bartenderLocations.ts` (`resolveGatewayUrl`/`listLocations`/`getLocationMap`/`getLocationZones`) is updated to the corrected gateway/header/response-shape findings above and live-verified for `/locations` and `/locations/{code}/zones`. The Site selector card and the Location map card's zone markers should now work end-to-end against Luc's sandbox tenant; the floor-plan image itself will still show the card's "couldn't load" state until the API key's Local Map read permission is granted on Bartender's side.

**API coverage audit, 2026-09-01** — the spec (`location-api-v2 (1).yaml`) defines 24 operations across 7 areas; this app calls **3**:

- **Implemented**: `GET /locations` (site selector, Devices' Site dropdown), `GET /locations/{code}/zones` (zone markers, the `PRESENT` Item Feed's zone picker), `GET /locations/{code}/map` (called, but blocked by the permission-scope `403` above — the floor plan actually shown comes from the unrelated legacy `statemachine-api-configuration` workaround, section 7.4, not this endpoint).
- **Never called**: the four read-only reference endpoints (`GET /reference/location-types(/…)`, `GET /reference/zone-types(/…)`) — this app hardcodes its own `DC`/`FACTORY`/`STORE`/`SUPPLIER`/`CUSTOMER` and Zone-type lists rather than fetching them, so it can't see a Zone Type's real EPCIS defaults (`defaultProcess`/`defaultStatus`) or a Location Type's allowed-Zone-Types constraint from the platform itself; Location write operations (`POST`/`PUT`/`DELETE /locations`) — this app only ever reads existing Sites, never creates/edits/deletes one on the real platform, consistent with its framing as a one-way test-data generator, not a site-configuration tool; Location Map write operations (`POST`/`DELETE /locations/{code}/map`) — same one-way-read posture; single-Zone `GET`, `POST`/`PUT`/`DELETE` on Zones — this app only ever lists Zones, never creates, reads, updates, or deletes one against the real platform; **all five Channel Mapping operations** (`GET`/`POST`/`GET one`/`PATCH`/`DELETE` under `/zones/{zoneCode}/mappings`) — see the note below, this is the biggest gap; CSV `POST /locations/import` / `GET /locations/{code}/export`.
- **A concrete lead for BL-070, surfaced by this audit**: `GET /locations/{code}/zones`'s real `Zone` schema carries a `bizLocation` field (an EPCIS SGLN-style identifier, e.g. `urn:epc:id:sgln:0614141.00001.1`) alongside the human-facing `zoneCode`/`zoneName` — but `lib/bartenderLocations.ts`'s `RawZone`/`getLocationZones` never reads or exposes it, only `zoneCode`/`zoneName`/`type`/`position`. Separately, `inventory-public-api`'s own top-level description states its data model is structured around **"Site (`bizLocation`), Zone (`bizLocation` sub-unit)"** — meaning `GET /stock`'s `zoneCode` filter is most likely meant to be keyed off a Zone's `bizLocation`-derived identifier, not its plain `code`. BL-070's blocked symptom (the zone picker's codes, e.g. `14527.2549.…`, don't match what `GET /stock` keys by, e.g. `DEMOTT.00005.…`) is consistent with the app comparing the wrong field on both sides. **UPDATE — live-checked 2026-09-01 (§13 entry, `scripts/verify-bl070-zone-match.ts`): this `bizLocation` hypothesis is WRONG.** `bizLocation` is the *site* id (`urn:mjx:site:loc:DEMOTT.00005.0`, identical on every zone of a site), not a per-zone key. The real cause: `GET /locations/{code}/zones` returns *two* entries per physical zone — a `14527.2549.<serial>` one and a `DEMOTT.00005.<n>` one, same `name` — and `GET /stock`'s `zoneCode` matches the `DEMOTT.00005.*`-form Location zone `code` **exactly**. Fix (not yet chosen by Luc): dedupe the picker toward the `DEMOTT.00005.*` code, and/or match stock by zone `name`. No internal-API workaround needed.

### 7.4 Legacy floor-plan map retrieval (Basic Auth) — temporary workaround, added 2026-08-28, live-verified same day

**Context**: section 7.3's `GET /locations/{code}/map` (`location-api-v2`) returns `403 Local Map[read]` for the current API key — a real permission-scope gap on Bartender's side, not something fixable from this app. Luc identified an alternate, older path to the same floor-plan image, using the already-integrated `statemachine-api-configuration` API (section 7.2) plus a second endpoint that only accepts a different auth scheme.

**1. Find the floor sub-location for a site.** `GET {tenantUrl}/statemachine-api-configuration/rest/configuration/locations?level=floor`, header `apikey: <user's key>` — identical auth to section 7.2's `level=premise` call, just a different `level`. Returns the tenant's floor-level locations (sub-locations of a premise/site), shaped like section 7.2's example (`id`, `code`, `name`, `level: "floor"`, `parent`, etc.).

**Matching corrected after live-testing 2026-08-28** — the original assumption (match the floor whose `name` equals the site's `name`) **does not hold**: checked against all 3 real seeded sites and the floor's `name` mirrors its own `code`, never the premise's display name.

| premise `code` | premise `name` | matching floor `code` | floor `name` |
|---|---|---|---|
| `TTMEMBASE` | `T&TMembase` | `TTMEMBASE_FLORR` | `TTMEMBASE` |
| `TANDTWAREHOUSE` | `T&TWarehouse` | `TANDTWAREHOUSE_FLOOR` | `TANDTWAREHOUSE` |
| `GRANITEFALLSSHOP` | `Granite Falls Shop` | `GRANITEFALLSSHOP_FLOOR` | `GRANITEFALLSSHOP` |

The reliable link is **structural**, not name-based: every floor's `parent` field holds the numeric `id` of its parent premise (confirmed across all 3 rows above). So the correct lookup is: fetch `level=premise`, find the entry whose `code` matches the site, take its `id`; fetch `level=floor`, find the entry whose `parent` equals that `id`. Implemented as `findFloorForPremiseCode(tenantUrl, apiKey, premiseCode)` in `lib/bartenderLocations.ts` (supersedes the originally-planned `findFloorByName`).

**2. Fetch the map for that floor.** `GET {tenantUrl}/statemachine-api-configuration/rest/configuration/locations/{floorLocationId}/maps` — **not** the `apikey` header this time. This endpoint only accepts **HTTP Basic Auth** (`Authorization: Basic base64(username:password)`) — a Track & Trace **login + password**, a credential type separate from the API key entirely.

**Response shape confirmed live 2026-08-28** (tested against `TTMEMBASE`'s floor, id `59414593393144`, with Luc's Track & Trace username/password): **`200`, raw image bytes directly** — `Content-Type: image/png`, a real 5718×3457 floor-plan PNG, not JSON metadata. This means the browser can't be simply pointed at the tenant URL directly (it doesn't hold the Basic Auth credentials, and shouldn't be given them) — the bytes must be proxied server-side through this app's own API and streamed back with the right `Content-Type`. See `app/api/locations/[code]/legacy-map-image/route.ts`.

**New credential requirement**: this Basic Auth login/password is a new, third Bartender credential type (alongside tenant URL and API key, section 7.1) — added to Settings → Bartender Connection as **Username** / **Password** fields, reusing the exact same `.field-block` pattern already used there. Stored the same way the API key is: `bartenderPasswordCiphertext` (AES-256-GCM via `lib/crypto.ts`), `bartenderUsername` stored in cleartext like `bartenderTenantUrl`. Unlike the API key, the password gets **no masked last-4 preview** — just a "set" / "not set" indicator, since there's no legitimate reason to surface any fragment of a login password in the UI. Explicitly scoped: **only this temporary maps workaround uses Basic Auth** — every other Bartender endpoint in this app keeps using the `apikey` header.

**This is explicitly temporary.** The moment Bartender grants this API key's `Local Map[read]` permission (section 7.3), the map card should revert to calling `location-api-v2`'s own `/locations/{code}/map` directly — the floor-lookup + Basic-Auth detour goes away entirely. Leave the Username/Password fields and schema columns in place rather than ripping them out the moment that happens (harmless if unused); just log a follow-up decision-log entry here once it's confirmed the permission gap is closed and the workaround has been removed.

### 7.5 DataCollector API (`datacollector-api-v3`) — provided 2026-08-28, full spec re-read and corrected 2026-08-29

Added directly to the claude.ai Project as `datacollector-api-v3 (2) (2).yaml`. Defines how a real reader or software collector registers itself with Bartender and submits tag reads — this is the API this app's own simulated `Device`/"Collector" concept (section 15) is modeled after. **Now called live by this app for registration only** (Publish/Delete, section 15.8, BL-053/BL-054) — heartbeat and read ingestion remain unmodeled, see below.

- **Server**: `https://api.bartender-tt.com/datacollector` — the spec lists only a "Production environment" here, unlike `location-api-v2` (section 7.3), which turned out to need a second `.sandbox.` gateway once tested live. **Confirmed by Luc 2026-08-29**: a sandbox gateway does exist for this API too, same pattern as `location-api-v2` — `https://api.sandbox.bartender-tt.com/datacollector`, selected the same way (`bartenderTenantUrl` contains `sandbox`). No longer an open risk; still worth a quick live sanity check the first time it's called, same as any endpoint.
- **Auth**: `apikey` header (this app's choice, 15.8), or HTTP Basic (`Authorization: Basic base64(username:password)` **plus** a required `x-tenant` header carrying the tenant code, e.g. `ACME`) — same two-scheme pattern as `location-api-v2` and the legacy maps endpoint (section 7.4). This app has no field storing a bare tenant code today (only the full `bartenderTenantUrl`), which is one more reason the `apikey` header — needing no `x-tenant` — is the simpler choice here.
- **Key concepts**: a **DataCollector** is a device or app, identified by a caller-chosen `collectorId`; a **Channel** is a logical stream of observations it produces (`PRESENCE` — reports tags currently in a Zone, needs `presenceEvent`, forbids `direction`; or `DIRECTIONAL` — reports tags crossing a boundary, needs `direction`, forbids `presenceEvent`); **read point type** (`GET /reference/read-point-types`) — confirmed to be the **exact same 13-code set** already integrated as `READ_POINT_TYPES`/`ReadPointIcon` (BL-029): `PORTAL`, `CONVEYOR`, `OVERHEAD`, `SHELF`, `TABLETOP`, `ENCLOSURE`, `DOORFRAME`, `LIFT_LOBBY`, `SIMPLE_READER`, `MIDDLEWARE`, `MES`, `WCS`, `APP`. This resolves BL-029's open question for good — read-point type and this app's Device `type` are exactly the same enum, straight from Bartender's own reference data.
- **`POST /collectors/register`** — the registration payload is what section 15's `Device` model is shaped after. Required: `collectorId` (unique within the tenant, stable across restarts and re-registrations), `locationId` (must match a Location's `code`, **and must match the Location scoped to the calling API key** — see the `403 LOCATION_MISMATCH` risk below), `model`, `readPointType`, `channels[]`. Optional: `collectorName`, `vendor`, `configVersion` (opaque version token — firmware version, timestamp, or hash; enables heartbeat `CONFIG_PENDING` change detection, see 15.8's version-management rule), `heartbeatConfig` (`{enabled, timeoutSeconds}`, defaults `true`/`120`), `attributes` (free-form flat key/value map — string/number/boolean values only, no nesting, both at collector and Channel level). Re-registration is idempotent on `collectorId` and **replaces the whole stored Channel list** — always submit the complete list, never a partial diff. Response includes a `reconciliation` object flagging any existing Zone mapping a re-registration affected: `CONFLICT` (mapped Channel still exists, config changed, needs review), `BROKEN` (mapped Channel was removed), `OFFLINE` (heartbeat timeout exceeded).
- **`DELETE /collectors/{collectorId}`** (not previously documented here) — permanently deregisters a DataCollector, removing its Zone mappings. Irreversible; re-registering the same `collectorId` afterward creates a fresh record rather than restoring the old one. Used by BL-054's opt-in delete flow (15.8).
- **`GET /collectors`** (tenant-wide, paginated, filterable by `locationId`/`readPointType`/`category`/`status`/`hasUnmappedChannels`) and **`GET /locations/{locationCode}/collectors`** (site-scoped) — both not previously documented here. **Deliberately not called by this app** (15.8) — Luc's explicit framing is a one-way push from the simulator's own Devices, never a pull/reconciliation against what's actually on the platform.
- **`403 Forbidden` / `LOCATION_MISMATCH`** (not previously documented here) — "the submitted `locationId` does not match the Location scoped to the API key." Read literally this could mean a key is scoped to one Location; **per Luc (2026-08-29), his understanding is that a Bartender API key is scoped to the tenant as a whole, not to an individual Location within it** — but this is still unverified against a real call, so 15.8 keeps it as a required live check before the real-publish feature ships, not an assumption either way.
- **`PUT /collectors/{collectorId}/heartbeat`** — heartbeat keepalive. **Called live since BL-072 (v0.24.0, section 15.10)** — separate from, and unaffected by, the `heartbeatConfig` object on `POST /collectors/register` (modelled and sent since 2026-09-08 — `{enabled, timeoutSeconds}`, §15.8's table; this endpoint's own body still takes only `timestamp`). **Live-verified 2026-09-01: the body accepts only `timestamp` (ISO-8601 UTC)** — `configVersion` and every other extra field are rejected `400 VALIDATION_ERROR "Unknown field."`, so the spec's `{ timestamp, configVersion?, activeChannels? }` was wrong. Response: `{ status: "ONLINE" | "CONFIG_PENDING", lastSeenAt }`; unregistered id → `404 COLLECTOR_NOT_FOUND`. Details in 15.10.
- **`POST /reads`** — tag-observation ingestion. **Now called live by the run engine (BL-063, 2026-08-31)** — every simulated read (an entry Feed Link firing and every downstream hop) is also submitted for real while its Workflow is RUNNING. Contract (from the YAML + live-probed 2026-08-31):
  - `POST {gateway}/datacollector/reads`, `apikey` header (Basic + `x-tenant` also supported, unused here).
  - Body: `{ collectorId, channelId, readTime (ISO date-time), tags: [ { <one of> epc | hexa | tid | uid | gs1_128, attributes? } ], transactionId? }`. `tags` min 1; exactly one identifier per tag.
  - **A Serialization-API SGTIN-96 hex goes straight into `hexa` as-is** (live-confirmed `COMMITTED`); a `urn:epc:id:sgtin:…` URN goes into `epc`. Bare hex in `epc`, or `urn:epc:tag:sgtin-96:…`, are rejected `400 VALIDATION_ERROR`.
  - `200` → `{ collectorId, channelId, tagsReceived, epcisEventId (string|null), status }` with `status` = `COMMITTED` (EPCIS event written) or `NOTPROCESSED` (channel has no active Zone mapping → observations discarded, **not an error**). `207` → per-tag `results[]` with `REJECTED` entries. `400`/`401`/`404` are real failures.
  - Failures never block the local simulation — they're counted in the tick summary (`readsPushed` / `readsNotProcessed` / `readsFailed`) with a note.
  - **`PRESENT` feeds now push for real (2026-09-02, BL-070).** Was: their batch items were placeholder ids because the Inventory API only exposed counts. Resolved by `POST /inventory/stock/analytics` with `dimensions: ["hexa", "product.pid"]` (§7.8) — that returns the individual 24-char SGTIN-96 EPCs in the zone, each of which drops straight into `hexa` on `POST /reads`. `resolveBatch`'s `PRESENT` branch now calls `getStockHexa()` (`lib/bartenderInventory.ts`), samples up to the feed's quantity, and pushes them through `sendReads()` exactly like a `NEW` batch. Still contingent on the zone actually accumulating stock platform-side.
- The real API's own Collector status (`ONLINE`/`OFFLINE`/`CONFIG_PENDING`, from heartbeat freshness and config-version drift) is **Bartender's** concept, entirely separate from this app's own 4-state Device visualization (section 15.3) — don't conflate the two even though both use similar-sounding words. **Revised 2026-08-31 (section 15.10)**: this app now sends real heartbeats for every published, heartbeat-enabled Device, so a correctly-running Device should read as Bartender-side `ONLINE`, not `OFFLINE` — but this still never feeds back into this app's own Active/Automated/Problem state (15.3), which stays purely local.

#### GS1 standard expansion (BL-089, 2026-09-17) — full `Gs1Standard` contract, `sscc-96`/`grai-96`/`giai-96`/`gid-96`/`dsgtin-plus`/`dsgtin-plus-plus`

- **A real inconsistency in the spec itself, flagged rather than silently resolved**: the formal `Gs1Standard` enum (used for request-path validation on `POST /gs1/{standard}/generate`) lists exactly **7** values — `sgtin-96`, `sgtin-198`, `sscc-96`, `grai-96`, `giai-96`, `dsgtin-plus`, `dsgtin-plus-plus`. **`gid-96` is not in that formal enum**, despite appearing in the endpoint's own prose/example response, the tutorial curl examples, a full request/response example fixture, *and* Luc's own live `GET /gs1/standards` response (which is what this app should trust operationally — it's the platform's own live answer, not the static spec doc). - **8 standards built, matching exactly what Luc's `GET /gs1/standards` response listed** — the formal 7 plus `gid-96`. Revisit only if Luc names one of these directly, the same posture as BL-073a.
- **This app still only ever requests `formats: ["hex"]`** — unchanged from BL-073, and confirmed to still be the sole format needed: every one of the 8 standards supports `hex` (the spec's own per-standard format restrictions only ever *remove* `epcUrn`/`epcTagUri` for some standards — e.g. dsgtin-plus/plus-plus never support those two — never `hex`). No `formats` picker added to the UI; `digitalLinkBaseUrl` stays unmodeled (only relevant to the `digitalLink` format).
- **`filter` (int 0–7) is now a real per-mint parameter this app must always supply explicitly** — the v3 API applies **no default**, unlike the old client's implicit omission. Recommended-by-spec defaults, pre-filled per standard in the Item Feed form but editable: `sgtin-96`/`sgtin-198`/`dsgtin-plus`/`dsgtin-plus-plus` → **3**; `sscc-96` → **0** (spec explicitly flags 3 as "semantically wrong" for SSCC; 0 or 1 are the documented options, 0 chosen as the more common logistics-unit default); `grai-96`/`giai-96` → **6**. **`gid-96`'s filter value isn't documented anywhere in the spec** (classic GID-96 doesn't carry a filter/partition structure the way GTIN-based schemes do) — defaulted to **0** as a placeholder, explicitly flagged as unconfirmed; live-verify against a real `POST /gs1/gid-96/generate` call before relying on it, and correct this note with whatever the platform actually accepts or ignores.
- **Per-standard `input` fields — new `ItemFeed` columns, only populated for the standard actually selected** (full field list is `Gs1InputFields` in the spec; only the subset these 8 standards actually use is modeled — `locationReference`/`serviceReference`/`documentType`/`couponReference`/`componentPartReference`/`pieceNumber`/`totalPieces`/`partyReference`/`customAIs` all belong to the out-of-scope standards above and are **not** added):
  - `sgtin-96` / `sgtin-198` — unchanged: `gtins` (existing field) + the existing `DEFAULT_COMPANY_PREFIX_LENGTH = 7` constant. No new fields.
  - `sscc-96` (logistic units — pallets, cases) — `companyPrefix` (6–12 digits) + `extensionDigit` (single digit string, default `"0"`, maps to the API's `extension` field). No GTIN.
  - `grai-96` (returnable assets) — `companyPrefix` + `assetType`. No GTIN.
  - `giai-96` (individual assets) — `companyPrefix` + `itemReference` (labeled "Individual asset reference" in the UI — the spec's generic field name, GIAI-specific meaning). No GTIN.
  - `gid-96` (general identifier — no company prefix at all, a wholly separate identifier family) — `generalManagerNumber` + `objectClass`. No GTIN, no company prefix.
  - `dsgtin-plus` / `dsgtin-plus-plus` — `gtins` (existing field, DSGTIN still embeds a GTIN) **plus** the new lot/date mechanism below (`Gs1Context`). ~~`dsgtin-plus-plus` additionally requires `customDomainName`~~ — **corrected 2026-09-17, see the "Live-testing findings" subsection immediately below**: there is no dedicated `customDomainName` field. `dsgtin-plus-plus`'s embedded-domain requirement is satisfied by the request's ordinary top-level `digitalLinkBaseUrl` field (defaults to `https://id.gs1.org`), sent whenever this standard is used — live-confirmed by a real mint that succeeded with no domain field inside `input`/`context` at all.
- **`companyPrefixLength`** — still only meaningful for the GTIN-splitting schemes (`sgtin-96`/`sgtin-198`; DSGTIN's `input.gtin` doesn't use it either — "the new EPC schemes do not use partition tables", spec's own words). Not sent at all for `sscc-96`/`grai-96`/`giai-96`/`gid-96`, which supply `companyPrefix` directly with no splitting needed.
- **DSGTIN's lot/date mechanism (`Gs1Context`)** — the part of Luc's request needing real design, not just a field pass-through:
  - **The date**: `Gs1Context` has seven possible "prioritised date" fields (`productionDate`/`packagingDate`/`bestBeforeDate`/`sellByDate`/`expirationDate`/`firstFreezeDate`/`harvestDate`) and the API requires **exactly one** — this is the actual date embedded in the EPC binary (GS1 TDS 2.0), enabling over-the-air RFID filtering like "select all tags expiring today". Luc named exactly two of the seven — **expiration date and best-before date** — so only those two are exposed; the other five stay unmodeled (available in the API, not in this app's UI, revisit only if Luc names one). New `ItemFeed.gs1DateField String?` (`"expirationDate"` | `"bestBeforeDate"`, DSGTIN-only) + `ItemFeed.gs1ShelfLifeDays Int?`.
  - **Luc's explicit ask, verbatim**: *"please ask for a period instead of a final date, the final date should be computed by adding this period to the current date."* So the stored value is a **duration**, not a date — modeled as a whole number of days (`gs1ShelfLifeDays`), with the form offering a friendlier number+unit input (days/weeks/months) that converts to days on save (months approximated as 30 days, weeks as 7 — a documented simplification, flagged rather than silently precise). The actual ISO `YYYY-MM-DD` value is **computed fresh at firing time**, every time the Feed fires: `today + gs1ShelfLifeDays` (server clock, at the moment `resolveBatch()`/`mintSerializedItems()` runs) — never computed at save time, never stored as a fixed date. This means two firings of the same Feed on different days produce different dates, which is the whole point (a shelf-life *policy*, not a one-off value).
  - **The lot code**: `Gs1Context.lotCode` (string, ≤20 chars, GS1 AI 10) is **optional** in the spec but Luc explicitly asked for it to be supported, plus "the base recommended GS1 lot code algorithm that includes month, day in it." **Framed honestly**: GS1's own General Specifications leave the Lot/Batch Number's *format* entirely to the assigning company — alphanumeric, ≤20 chars, no mandated structure, no check digit. There is no single "official" GS1 lot-code algorithm to point to. What's proposed instead is a **common, sensible convention**, offered as an editable default rather than an enforced rule (same "auto-suggest, never enforce" posture as `collectorId`, BL-050):
    ```
    L<YYMMDD><-><3-char uppercase alphanumeric>
    e.g.  L250917-K3M
    ```
    `YYMMDD` is the date the lot code is generated (2-digit year, 2-digit month, 2-digit day — satisfies Luc's explicit "includes month, day" ask, and the year keeps it unambiguous across a full year of test data); the 3-char suffix is a random uppercase-alphanumeric tie-breaker so two lots minted on the same day don't collide. 11 characters total, well under the 20-char cap, and sorts/reads sensibly. **Two modes on the Feed**, mirroring the date mechanism's "computed fresh" spirit while still giving Luc a fixed-lot option: `ItemFeed.gs1LotMode` `"AUTO"` (default) generates a fresh lot code with this algorithm **at firing time** (so the embedded date tracks the actual firing day, same reasoning as the shelf-life date above) — vs. `"FIXED"`, where `ItemFeed.gs1LotCode` holds one user-entered-or-suggested string reused by every firing (a "Suggest" button in the form runs the same algorithm once, then the field is freely editable). Either way `lotCode` is optional per the spec — a Feed can also carry no lot code at all.
- **Response handling unchanged**: `serials[].hex` parsed exactly as today, regardless of standard; DSGTIN's echoed `context` isn't stored (nothing downstream currently needs to read a lot/date value back off a minted item).
- **Deliberately deferred, not built**: `customAIs` (freeform AI-number→value map — too open-ended relative to what Luc actually asked for, revisit only if a concrete AI is named); `ilmd` (a separate, still-unmodeled instance-level-master-data mechanism with its own overlapping lot/date/weight fields — DSGTIN's `context` is the mechanism Luc's request actually maps onto, not `ilmd`); `serialSource` modes other than `internal` (documented as future in the spec, not implemented API-side either); non-`hex` `formats` (see above).
- **`companyPrefix` validation**: 6–12 digits (spec pattern), enforced the same way `gtin`'s pattern is today — a 400 from `buildItemFeedData`, not a round-trip to the platform to find out.

### 7.8 Inventory API (`inventory-public-api`) — added to the project 2026-08-30

Feeds the **Item Feed** entity's `PRESENT` kind — this is the "Stock API" referenced when that kind was first discussed (Luc: "reuse existing products of the same GTINs present in a zone... through the Stock API I will add to the project").

- **Server**: the spec lists only `https://api.bartender-tt.com/inventory` (Production) — no sandbox variant shown in the spec text. Given `location-api-v2` and `datacollector-api-v3` both turned out to need a `.sandbox.` counterpart once tested live (7.3/7.5), assume the same `api.sandbox.bartender-tt.com/inventory` pattern applies here until a live call confirms or corrects it.
- **Auth**: the spec's own description says both **HTTP Basic and an `apiKey` header** are required together — a third auth pattern, distinct from the bare-`apikey`-header scheme (7.2/7.3/7.5) and the pure-Basic scheme (7.4/7.6/7.7). One parameter example in the spec also shows an `x-tenant` header. Needs a live call to pin down exactly which headers this app must actually send together; don't guess further than what's written here.
- **Key endpoint — `GET /stock`**: filters `locationCode[]`, `zoneCode[]`, `sku[]`, `pid[]` (PID = GTIN), `groupBy` (`sku`/`pid`/`zone`, default `sku` — an Item Feed's `PRESENT` lookup should use `groupBy=zone` plus `zoneCode`+`pid`), `inStockWindowDays` (an item only counts as in-stock if its most recent EPCIS event falls inside this look-back window — this is a Bartender-side setting this app just passes through, not something to hardcode), pagination (`page`/`pageSize`). Response: `{ groupBy, inStockWindowDays, asOf, page, pageSize, total, results: [{ locationCode, locationName, zoneCode, zoneName, sku, pid, productLabel, qty, lastSeenAt }] }`. An empty `results` (or `qty: 0`) is exactly the "nothing to scan this run" case Luc described for `PRESENT`.
- Also exposes `GET /stock/export` (CSV) and `POST /stock/analytics` — the latter turns out to be **the fix for the counts-not-EPCs `PRESENT` limitation** (live-probed 2026-09-02, Luc's lead; **wired into the run engine the same day — BL-070 done, v0.30.0**):
  - `POST {gateway}/inventory/stock/analytics`, bare `apikey` header (same as `/stock`). Body: `{ inStockWindowDays, filters: [{ field, operator, values }], dimensions: [...], metrics: ["itemsQty"], sortBy?: { itemsQty: "DESC" } }`.
  - **`dimensions: ["hexa"]` returns the individual EPC hex strings in stock** — `{ page, pageSize, inStockWindowDays, total, results: [{ hexa: "3034DF97…" (24-char SGTIN-96), qty: 1 }] }`. Each `hexa` drops straight into `POST /datacollector/reads`'s `hexa` field (§7.5) — so a `PRESENT` feed can now pull **real** EPCs and push **real** reads, no more placeholder ids.
  - **`dimensions: ["hexa", "product.pid"]`** adds the GTIN per EPC — `{ pid: "03663328010013", hexa: "3034DF97…", qty: 1 }` — so per-item GTIN routing (§16.5) still works. `dimensions: ["product.pid"]` alone gives grouped counts per GTIN (`{ pid, qty }`). `product.pid` also works as a **filter** `field` (`{ field: "product.pid", operator: "eq", values: [<gtins>] }`) — so GTIN_LIST-mode `PRESENT` filters to its GTINs, ALL-mode drops that filter.
  - **Valid `dimensions`** (probed): `hexa`, `product.pid`, `zone.code`, `location.code`. Bare `pid`/`gtin`/`sku`/`zone`/`location`/`product`/`epc` → `406 Invalid dimensions` (the working names are dotted: `product.pid`). **Valid `metrics`**: only `itemsQty` (anything else → 500). **`filters`** `field` values: `location.code`, `zone.code`, `product.pid`; `operator: "eq"`.
  - **Pagination is ignored** — `pagination.documents`, `pageSize`, `page` in the body have no effect; the response is always `page:1, pageSize:100` with up to 100 rows. `total` gives the real count. Since BL-070b a take-all `PRESENT` firing pushes every returned row (capped at that 100 ceiling — a firing over it is rare here and not worth paging for); a capped firing slices to `quantityMax` client-side.
  - **`inStockWindowDays` — match the tenant config by reading it off `/stock`.** The analytics call requires (or at least should carry) this value; the tenant's configured default isn't exposed by a settings endpoint (`/settings`, `/inventory/config`, … all 404). But **`GET /inventory/stock` echoes the tenant's configured `inStockWindowDays` in its response envelope** when the param is omitted (`{ …, "inStockWindowDays": 30, "asOf": … }`); passing `?inStockWindowDays=7` makes it echo the override instead. So: one cheap `GET /inventory/stock?groupBy=zone&pageSize=1` per tenant per tick → read `body.inStockWindowDays` → pass it into the analytics `POST`. Omitting it from the analytics body also returns 200, but the response then doesn't echo the window used, so reading it from `/stock` first is the reliable path.
- **2026-08-31 — `PRESENT` / "In stock" feed is blocked by a zone-code mismatch (traced live).** The zone selector in the Item Feed form is populated from **`location-api-v2`** `GET /locations/{code}/zones`, which returns zone codes like `14527.2549.24940050679000088` (name `MINILOAD`). But `GET /inventory/stock` keys its rows by codes like `DEMOTT.00005.1000000000023`. They don't line up, so `getStock` filtered by any zone the form offers returns 0 rows → `resolveBatch` produces an **empty batch** → nothing fires and nothing is pushed (the run engine writes an `n=0` `SimulatedRead` each firing and skips `sendReads`). **Luc's read (2026-08-31): this is a bug in the Location API** — a zone's `code` should equal its `name` most of the time; the `DEMOTT.00005.xxxx` values are **bizLocation** identifiers and should not be exposed as zone codes at all. Pending Luc's decision on whether to take a **temporary route via internal APIs** instead of the public ones. Do not rework the zone picker or the PRESENT path until he advises.
- **~~Separately — even with a matching zone, `PRESENT` can't push real reads.~~ Resolved 2026-09-02 (BL-070).** Was: `GET /stock` returned aggregate **counts, not individual EPCs**, so `resolveBatch` fabricated placeholder ids (`present:<zone>:<ts>:<i>`) that the platform 400'd. Now `resolveBatch`'s `PRESENT` branch calls `getStockHexa()` → `POST /inventory/stock/analytics` (`dimensions: ["hexa", "product.pid"]`, above), gets the real 24-char SGTIN-96 EPCs in the zone with their GTINs, samples up to the feed's quantity, and hands them to `sendReads()` — which `tagForItem()` now routes to `{ hexa }` (16+-char even-length hex), so they `COMMIT` for real just like a `NEW` batch. The placeholder-id path is gone; `emitReadAndScheduleHops` pushes any `PRESENT` firing with a `collectorId` and ≥1 item. Still contingent on the zone accumulating stock platform-side (a Receiving-type zone that discards bare presence observations still yields 0 rows — a platform-config matter, not a simulator one).

### 7.9 EPCIS Core API (`epcis-core`) — provided 2026-09-02, for the History page's EPCIS tab (BL-076a)

Feeds the History page's EPCIS-events tab (§19) — browsing the real events this tenant has recorded on the Track & Trace platform, not something this app writes to. Provided as two worked `curl` examples (no formal OpenAPI spec doc in the project), one unfiltered and one filtered by `premise` — both otherwise identical, so the filter set is additive/optional, not two different endpoints.

- **Endpoint**: `POST {bartenderTenantUrl}/epcis-core/rest/events/searches` — **tenant-relative** (the tenant's own host, e.g. `https://demotrackandtrace.sandbox.bartender-tt.com`), same pattern as the legacy Product API (7.7) and the floor-map workaround (7.4), **not** the fixed `api[.sandbox].bartender-tt.com` gateway host used by 7.2/7.3/7.5/7.6.
- **Auth**: HTTP Basic, reusing the already-stored Track & Trace username/password (7.4's credential pair) — no new credential type needed. (Luc's example curl carries a live `Authorization: Basic …` value of his own for testing; that value is not stored anywhere in this app — it authenticates as `TTGlobalMgr`, unrelated to any per-user stored credential, and must never be hardcoded into the codebase.)
- **Request body**:
  ```json
  {
    "filters": [
      { "property": "type", "operator": "WD", "values": ["*Event"] },
      { "property": "premise", "operator": "EQ", "values": ["<LOCATION_CODE>"] }
    ],
    "order": { "property": "eventTime", "direction": "DESC" },
    "pagination": { "documents": 20, "page": 0 }
  }
  ```
  - The `type`/`WD`/`["*Event"]` filter is always included — `WD` = wildcard, matching every EPCIS event type (`ObjectEvent`, `AggregationEvent`, `TransactionEvent`, `TransformationEvent`, …) in one filter rather than enumerating them.
  - The `premise`/`EQ` filter is **optional** — included only when a specific Location is selected in the tab's Location dropdown (§19), omitted entirely for "All Locations" (confirmed by Luc's own two examples — the unfiltered one simply drops that filter object, not passes an empty/wildcard value).
  - `<LOCATION_CODE>` — Luc's example uses `TTMBASE`; **not confirmed live** which field of this app's own `Location` data that corresponds to, but the strong candidate is `BartenderLocation.code` from `location-api-v2` (§7.3) — the same field this app already calls a site's "premise" internally (`findFloorForPremiseCode`, §7.4). Given this project's own history of same-looking codes turning out to key different things across different Bartender APIs (§13's 2026-09-01 BL-070 finding), **live-verify this correspondence with one real call before trusting it** — fetch a small unfiltered page, note a real event's `premise` value, and confirm it matches a known site's `code` before wiring the dropdown's filter through blindly.
  - `pagination.documents`: Luc's own examples use `100`; this app uses **`20`** (his literal "last 20 EPCIS events" ask) as a small named constant, easy to raise later if he wants more.
- **Response shape — LIVE-PROBED 2026-09-02** (`demotrackandtrace.sandbox`, before writing `lib/bartenderEpcis.ts`):
  ```json
  { "events": [ { /* event */ } ], "hasmore": true, "page": 0 }
  ```
  The envelope key is **`events`** (not `documents` as the request's `pagination.documents` key hinted — that guess was wrong). Each event:
  ```json
  { "id": "ObjectEvent-1788368992000-…", "type": "ObjectEvent",
    "eventTime": "2026-09-02T17:09:52.000+0000", "recordTime": "…",
    "bizStep": "urn:epcglobal:cbv:bizstep:commissioning",   // or urn:mjx:epcis:bizstep:serializing, :receiving, :unpacking
    "disposition": "urn:epcglobal:cbv:disp:active", "readPoint": "3",
    "bizLocation": "urn:mjx:site:loc:LATAMPOC.00008.1000000000001",
    "premise": "TTMEMBASE" | null, "action": "ADD", "bizTransList": [],
    "extension": { "mjx_user": "…", "___logicalReader": "TTMEMBASE-TABLETOP-02.__CH1", … },
    "epcList": [ { "epc": "urn:epc:id:sgtin:…", "gtin": "…", "sku": "…", "hexa": "…", "tid": null } ],
    "ilmd": { "countryOfOrigin": "Italy" } }
  ```
- **Item count**: this tenant's events (tool-generated reads and platform serialization events alike) all carry **`epcList`** — count = `epcList.length`. No `quantityList` seen. (`quantityList` support kept defensively in the type but not relied on.)
- **`premise` ↔ `Location.code`: CONFIRMED live 2026-09-02.** Filtering `premise EQ "TTMEMBASE"` returned only events whose `premise` field was exactly `"TTMEMBASE"` — the plain site code from `location-api-v2` (§7.3). The BL-070 zone-code mismatch does **not** recur here; the Location dropdown filter is wired straight through as `premise`. Note many events (`commissioning`/`serializing` steps) have `premise: null` and so appear only under "All Locations".
- **Human-readable event name**: `<type>` plus a formatted `bizStep` (a URN like `urn:epcglobal:cbv:bizstep:shipping` in the wider EPCIS standard — take the last path segment for the display label, e.g. "ObjectEvent — shipping"). No existing bizStep-formatting helper anywhere in this app yet (checked) — a small new one, not a reuse.
- **Not yet explored**: single-event lookup by id, any `documentType`/other filter properties beyond `type`/`premise`, and whether this app's own generated reads (BL-063's `sendReads` push) are reliably visible here shortly after a workflow fires — worth confirming once wired, as a natural end-to-end sanity check (fire a workflow, then reload this tab and see the new event appear).

### 15.1 Device model redesign — Collector fields, single default Channel

BL-036's minimal `Device` model (`id`/`name`/`type`/`locationCode`/`positionX`/`positionY`/`status`) is extended to carry the fields a real Collector registration (section 7.5) requires, so a Device is realistic enough to eventually be registered for real:

- `collectorId` (string, unique, nullable until configured) — the Bartender-facing stable id a real registration would use.
- `name` — already existed; now understood as `collectorName`.
- `type` — already existed (`READ_POINT_TYPES`); now confirmed identical to the DataCollector API's `readPointType` enum (section 7.5).
- `model`, `vendor`, `configVersion` — new, optional strings, straight from `CollectorRegistration`.
- `heartbeatEnabled` (default `true`), `heartbeatTimeoutSeconds` (default `120`) — flattened from the API's `heartbeatConfig` object.
- `attributes` (`Json?`) — free-form scalar key/value metadata, same shape/purpose as the API's `attributes`.
- **Channels — a real, repeatable list** (revised 2026-08-28, this batch — see BL-049): `channels` (`Json?`), an array of `{ id, name?, type: "PRESENCE" | "DIRECTIONAL", presenceEvent?, direction? }` entries. `id` is a simple per-Device sequence (`CH1`, `CH2`, …) — deliberately **not** derived from `collectorId`, so Channel identity stays stable even if the Collector ID is edited later. `name` (optional, added 2026-08-28 same day, BL-049a) is a freeform editable label, e.g. "Entry sensor" — same id/name split as Device's own `collectorId`/`name`, purely organizational. `type` selects which of `presenceEvent` (`FIRST_SEEN`/`PRESENT`/`LAST_SEEN`, `PRESENCE` only) or `direction` (`INBOUND`/`OUTBOUND`, `DIRECTIONAL` only) applies. A brand-new Device still starts with exactly one auto-added `PRESENCE`/`PRESENT` Channel — same zero-extra-clicks default as v1 — but the config screen (15.4) now supports adding, editing, and removing further Channels; at least one is always required. Kept as a flat JSON array rather than a proper `Channel` table, same reasoning as `attributes`: nothing here needs cross-Device Channel querying yet, and it keeps this a single-column migration. **Supersedes** the "single default Channel, not user-edited" v1 scope decision originally recorded here.
- **`collectorId` is now auto-suggested** (added 2026-08-28, BL-050): once Read point type and Site are both set and the field is empty, the config screen proposes `{locationCode}-{TYPE}-{NN}` (e.g. `TTMEMBASE-PORTAL-02`) — `NN` a 2-digit sequence, next-available per Site+Type pair across *all* Devices (configured or still a bare shell, so numbers never collide with an in-progress one). Purely a starting suggestion — always freely editable or replaceable, never enforced or validated as unique beyond the DB's own `@unique` constraint on the column.
- `configured` (boolean, default `false`) — unchanged from v1: **explicitly set**, not derived from `collectorId`'s presence, becomes `true` once the config screen's (15.4) required fields are saved.
- **`publishedAt` (`DateTime?`, added 2026-08-28, BL-051)** — null until the Device is explicitly **published to the platform** (15.4). This, not `configured` alone, is what the 4-state model (15.3) now gates its grey/not-grey boundary on: a Device can be fully `configured` and still show as grey "Not configured" until someone actually publishes it — matching Luc's own framing that "not configured" means *not live on the platform yet*, regardless of whether the form itself is complete. **Redefined 2026-08-29 (BL-053)**: originally a local, simulated status flip with no real call — now set only once `POST /collectors/register` actually succeeds against the real Bartender platform. See 15.8 for the full real-publish/sync design, including three new fields tracking sync health (`lastSyncedAt`, `lastSyncError`, `platformReconciliation`).
- `workflowId` (nullable, FK to the new `Workflow` model, 15.2) + relation.
- **`offlineAt` (`DateTime?`, added 2026-09-02, BL-074)** — null unless the owner has manually turned the Device off (§15.3's Offline state). Only meaningful when configured+published, and ignored entirely while the Device is Active (a running Workflow always wins); **not** cleared when a Workflow start overrides it, so it's restored once that Workflow stops. Set via `PATCH /api/devices/[id]/offline` (`{ offline: boolean }`), owner-only, 409 unless the Device is currently Ready or Offline.
- `locationCode`/`positionX`/`positionY` unchanged from BL-036.
- The old `status: DeviceStatus` (`ONLINE`/`OFFLINE`) field and `DeviceStatus` enum are **removed** — superseded entirely by the derived 4-state model (15.3), which factors in `configured` and `workflow.status` rather than a flat online/offline flag.

This is a breaking schema change to BL-036's `Device` table — existing seeded fixture rows need re-seeding with real values for the new required-shaped fields (Channel defaults), not a mechanical column rename.

### 15.2 Minimal `Workflow` model — pulled forward from section 6

**Explicit choice made with Luc**: rather than a cosmetic "in a workflow" flag on Device, a real (if intentionally minimal) `Workflow` model is introduced now — same reasoning as BL-036 pulling `Device` forward ahead of BL-003. This is **not** the real workflow engine (section 6, still fully open — step chains, device assignment logic, execution) — just enough of a `Workflow` entity that (a) a Device can be genuinely attached to one via `workflowId`, and (b) that workflow can be `RUNNING` or `STOPPED`, which is what drives the Automated/Problem device states (15.3):

```prisma
enum WorkflowStatus {
  RUNNING
  STOPPED
}

model Workflow {
  id        String         @id @default(cuid())
  name      String
  status    WorkflowStatus @default(RUNNING)
  createdAt DateTime       @default(now())
  updatedAt DateTime       @updatedAt

  devices Device[]
}
```

No Workflow creation/editing UI is in scope here — Workflows exist for now only as seed/fixture data (a couple of named fixtures, one `RUNNING` and one `STOPPED`, so the config screen's Workflow picker and all four device states are demonstrable end to end). Real Workflow authoring is section 6's job, whenever it's tackled.

### 15.3 Device state — four states, derived not stored

A pure function (`lib/deviceState.ts`, not a stored column) computes one of four states from `configured`, `publishedAt`, `offlineAt`, and `task?.workflow?.status`. **Revised 2026-08-28 (BL-051)**: gating moved from `configured` alone to `configured && publishedAt`. **Revised again 2026-09-01 (BL-074)**: renamed to match how Luc actually refers to these states, retired the old `Problem` state, added a manual `Offline` state, and made the running-workflow state visually distinct via animation rather than a lighter color. Precedence matters — checked top to bottom:

| State | Condition | Color |
|---|---|---|
| **Pending** ("Not configured") | `!configured \|\| !publishedAt` | Dark gray (`--device-pending`) |
| **Active** | `configured && publishedAt && task.workflow.status === "RUNNING"` | Full green, **animated** (`--device-active`) |
| **Offline** | `configured && publishedAt && offlineAt != null` (and not Active — see below) | Red (`--device-offline`) |
| **Ready** | everything else (`configured && publishedAt`, not Active, not Offline) | Full green (`--device-ready`) |

`Active` is checked *before* `Offline` — a running Workflow always overrides a manual Offline flag, so a Device can't get "stuck" red while genuinely part of a live run. `offlineAt` itself is not cleared when this happens, so if that Workflow later stops, the Device reverts to **Offline**, not Ready — it respects the last thing the user explicitly chose rather than silently discarding it. `Ready` now covers both "no Workflow attached" and "Workflow attached but stopped" — the old `Problem` state ("today red meant the workflow is not running") is gone; Luc's own words: "when the workflow is not running, the device turns into Ready."

A Device only reaches `Offline` by an explicit user action (new toggle, §15.6/15.7) — it can only be set from `Ready`, never from `Pending`, and never directly from `Active` (an Active Device can only be taken offline by stopping its Workflow, not individually — see §15.6).

**Revised 2026-09-08 (BL-086, §13):** `Offline` is now the **default**, not an exception. A Device starts `Offline` on first publish (`lib/deviceSync.ts`), and everything currently Online was backfilled to `Offline` (migration `add_device_auto_offline`). Being `Ready`/Online is always a **bounded window**: turning a Device on (single toggle §15.6/15.7, or the per-site panel §15.5a) sets `Device.autoOfflineAt = now + 60min`, and the heartbeat tick (§15.10) flips it back to `Offline` once that passes — so an unused simulator stops sending heartbeats on its own (Neon compute burn, §13). `autoOfflineAt` is cleared whenever the Device goes `Offline` (manually or by the sweep). The state function itself is unchanged — it still reads only `offlineAt` — `autoOfflineAt` is just the pending revert time.

**Known gap, not fixed by BL-074**: the run engine (`lib/workflowRun.ts`) doesn't check Device state before firing a Task's channel — an `Offline` Device attached to a running Workflow still has its reads processed exactly as if it were Active. Logged as `BACKLOG.md` BL-074a, not built.

Used everywhere a Device renders as a colored marker or badge: the Overview map (15.5/15.6) and the Devices list (15.7). See `CHARTE-GRAPHIQUE.md` "Device states" for exact token values and the animation spec.

**Consequence for BL-039's "Devices online" KPI**: counts Devices in the **Ready**, **Active**, or **Offline** state (i.e. configured+published, regardless of workflow/offline toggle) out of the site's total — unchanged in spirit from the original "configured, regardless of workflow" definition, just spanning the renamed/added states.

### 15.8 Real platform publish & sync — `POST /collectors/register`, `DELETE /collectors/{collectorId}` (BL-053/BL-054, added 2026-08-29)

**Supersedes** the "no real Bartender DataCollector call is made anywhere in this app" framing at the top of section 15 and in BL-042/BL-049's original decisions — for the Publish and (optionally) Delete actions only. Decided 2026-08-29, direct request from Luc: "publish the collector to the platform for real, using the data collector API," keeping the simulator's Devices "in sync with the ones that are really published in the platform (uniqueness comes from the CODE and the LOCATION)." Two things Luc was explicit about scoping *out*: platform-side collectors that don't correspond to a simulator Device are never surfaced or reconciled ("ignore them") — this is a one-way push (simulator → platform), never a pull; and the simulator only ever considers Devices it defined itself, never queries `GET /collectors`/`GET /locations/{code}/collectors` to discover or adopt anything.

**Auth & gateway** — reuses the same per-user Bartender Connection credentials as every other integration in this app (section 7.1): `bartenderTenantUrl` + the encrypted `apikey` (never Basic Auth for this API — no reason to take on the extra `x-tenant` header when the simple scheme already works for `location-api-v2`). Gateway resolution mirrors `lib/bartenderLocations.ts`'s `resolveGatewayUrl` pattern: sandbox when `tenantUrl` contains `sandbox`, production otherwise — **confirmed by Luc 2026-08-29** that a sandbox gateway (`https://api.sandbox.bartender-tt.com/datacollector`) does exist for this API, same pattern as `location-api-v2`. No longer an open risk.

**Field mapping** (Device → `CollectorRegistration`, section 7.5):

| Device field | API field |
|---|---|
| `collectorId` | `collectorId` |
| `name` | `collectorName` |
| `locationCode` | `locationId` |
| `model`, `vendor` | `model`, `vendor` |
| `type` | `readPointType` |
| `configVersion` | `configVersion` |
| `attributes` | `attributes` |
| `heartbeatEnabled`, `heartbeatTimeoutSeconds` | `heartbeatConfig.enabled`, `heartbeatConfig.timeoutSeconds` |
| `channels[]` (`id`, `type`, `presenceEvent`/`direction`) | `channels[]` (`channelId`, `channelType`, `presenceEvent`/`direction`) |
| `channels[].name` (BL-049a, simulator-only label) | `channels[].attributes.label` — the real API has no channel-name field, so a Channel's local label rides along as a flat channel-level attribute rather than being dropped silently |

`collectorId` doubling as the uniqueness key already satisfies Luc's "uniqueness comes from the CODE and the LOCATION": this app's `collectorId` column is `@unique` **and** BL-050's auto-suggested scheme always bakes the Site into the code itself (`{locationCode}-{TYPE}-{NN}`), so two Devices can never collide on `(collectorId, locationCode)` even though the DB only enforces uniqueness on `collectorId` alone. Publishing requires a non-empty `collectorId` — enforced client-side before the call is attempted, same required-field pattern as `name`/`locationCode`.

**`model` is required to publish (live-probed 2026-09-08, §13).** The new sandbox `datacollector-api` version rejects a register with a blank `model` (`VALIDATION_ERROR: model must not be blank`) — it was optional in Phase 0. Enforced now the same way `collectorId` is: `lib/deviceConfig.ts` `validateModelForPublish(body, willSync)` returns a 400 from both device routes on any syncing save (Publish, or Save on an already-published Device) with no `model`; the config modal blocks the same case client-side and shows the Model field as `Model *` once the Device is published. A local-only draft still saves without one. `vendor` was not confirmed required (the `model` check fires first and short-circuits).

**`heartbeatConfig` is sent on every register (live-probed 2026-09-08, §13).** Phase 0 (BL-053) left it out because its shape was unknown; the new sandbox version accepts it as a closed schema — exactly `{ enabled: boolean, timeoutSeconds: integer > 0 }` — and echoes it back on `GET /collectors/{id}`. `buildCollectorRegistrationPayload` now always emits `heartbeatConfig: { enabled: device.heartbeatEnabled, timeoutSeconds: device.heartbeatTimeoutSeconds }` (a non-positive stored timeout falls back to 600, since the platform 400s on `0`). It's sent unconditionally rather than only when "enabled", because a register that omits `heartbeatConfig` doesn't reset it cleanly on the platform side (observed: `timeoutSeconds` retained, `enabled` reset to its `true` default). **Gateway-version safety:** the sandbox gateway (`api.sandbox.bartender-tt.com`) is on this newer version; whether `api.bartender-tt.com` is too is unverified. `registerCollector` therefore retries once **without** `heartbeatConfig` if a register 400s specifically with an unknown-field error naming `heartbeatConfig` — so a not-yet-upgraded gateway still publishes fine, just without the config sync. See §15.10.

**Config version, managed automatically but always overridable (Luc's explicit ask)** — `configVersion` stops being a plain free-text field and gains real version semantics:
- **On creation**: if left empty, defaults to `"1"`.
- **On every save that syncs to the platform** (Publish, or Save on an already-published Device): if the submitted `configVersion` is unchanged from what's stored, it's auto-incremented before the call is sent — parsed as an integer and bumped by one (`"3"` → `"4"`); a non-numeric stored value (something Luc typed by hand) is left as-is rather than guessed at.
- **Whenever the submitted value differs from what's stored** (Luc edited the field himself), that typed value wins outright — no auto-increment on top of a manual edit, this save and no further ones until it's next left unchanged.
- A **draft** save (unpublished Device, "Save draft") never touches `configVersion` beyond persisting whatever's in the field — no auto-increment, since nothing is being sent to the platform.

**Register call outcomes** — `POST /collectors/register` is idempotent on `collectorId` (section 7.5), so the same call shape works for both the first Publish and every later resync:
- `201 REGISTERED` or `200 UPDATED` → success. Set `lastSyncedAt` to now, clear `lastSyncError`, store the response's `reconciliation` block (if any) as `platformReconciliation`. Set `publishedAt` to now **only if it was still null** (first publish) — never touched again after that by a successful resync.
- Any other response (`400 VALIDATION_ERROR`, `401`, `403 LOCATION_MISMATCH`, network failure, …) → the local config save still goes through in full; `publishedAt` and `lastSyncedAt` are left exactly as they were (a failed resync never un-publishes a Device that was already live); `lastSyncError` is set to a plain-language message built from the response (mirroring `POST /api/settings/bartender/test`'s existing error-message conventions), surfaced as an `.error-banner` inside the config modal so a sync failure is never silent. `reconciliation`-flagged Channels (`CONFLICT`/`BROKEN`) from a *successful* call are called out per-Channel-row in the same modal, not just logged.

**Flagged risk — Location-scoped API keys**: the spec's own `403 LOCATION_MISMATCH` is defined as "the submitted `locationId` does not match the Location scoped to the API key" (section 7.5) — read literally, this could mean a Bartender API key is authorized for only *one* Location. **Per Luc (2026-08-29), his understanding is that the key is scoped to the tenant as a whole, not to an individual Location** — matching how this app's stored credential works today (one API key per user, used across all three seeded sites for `location-api-v2` calls without issue). Still, this is his understanding, not yet a live-confirmed fact for this specific API — **must be live-verified against Luc's sandbox tenant before this feature is considered done**: attempt a real register call at two different `locationId`s with the same stored key and confirm both succeed. If — against Luc's own expectation — only one does, that's a real platform constraint to surface to him plainly (e.g. Publish only works at whichever Location the key is bound to, with a clear error elsewhere), not something to build around silently.

**Deregister on delete (BL-054)** — `DELETE /collectors/{collectorId}` is genuinely irreversible on Bartender's side (drops Zone mappings; re-registering afterward creates a fresh record, it doesn't restore the old one). Per Luc's answer when asked, this is **opt-in per delete, asked every time** — never automatic, never a stored preference: deleting a published Device asks a plain yes/no after the usual delete confirmation ("Also deregister it from the real Bartender platform? This can't be undone on their side."). The local Device row is deleted either way; a failed remote deregister call (key rejected, network error, collector already gone) doesn't block the local delete — it surfaces as a follow-up warning that the platform-side record may still exist.

**Deliberately not built here**: any UI or logic that calls `GET /collectors` or `GET /locations/{code}/collectors` to list, reconcile, or adopt platform-side collectors — Luc was explicit that unmatched platform collectors are simply ignored, and the simulator's own Device table is the entire source of truth for "our" collectors. Read ingestion went live 2026-08-31 (16.5, BL-063) and heartbeat the same day (15.10, BL-072) — both independent of this registration flow.

### 15.9 Cloning a Device — Duplicate (list) and Copy / Paste / Duplicate (map context menu), added 2026-08-31

Decided 2026-08-31, direct request from Luc: a fast way to clone an existing Device instead of re-entering every field by hand. Two entry points — the Devices list (15.7) and the Overview map (15.5) — share one server-side operation.

**What a clone copies vs. resets** — new `POST /api/devices/[id]/duplicate`:

- Copied verbatim: `type`, `locationCode`, `model`, `vendor`, `configVersion`, `heartbeatEnabled`, `heartbeatTimeoutSeconds`, `attributes`, `channels`, `configured` — the clone is exactly as "finished" as its source (a bare shell clones to another shell; a fully configured Device clones to another fully configured one).
- `name` becomes `"{source.name} (Copy)"`, literally — Luc's own wording ("we add (Copy) to the name"). Not de-duplicated further if a Device (or one already named "… (Copy)") is cloned again; a second clone reads "… (Copy) (Copy)". Accepted as-is, not worth guarding against for v1.
- `collectorId` is always **regenerated**, never copied — reuses BL-050's existing `{locationCode}-{type}-{NN}` sequence (next-available `NN` for that Site+Type pair, same logic `GET /api/devices/suggest-code` already computes) rather than duplicating that logic. Copying it verbatim would violate the column's own `@unique` constraint outright, so this isn't optional.
- **Publish state always resets, regardless of the source's own state** (explicitly confirmed with Luc): `publishedAt`, `lastSyncedAt`, `lastSyncError`, `platformReconciliation` all start `null` on the clone. Cloning an already-published Device never auto-registers the copy on the real Bartender platform — it reads Off/"Not configured" until someone explicitly publishes it, exactly like any other new Device. Keeps every real platform write behind an explicit user action, same posture as 15.8.
- The `task` relation (section 16 — Workflow attachment) is never copied. A clone always starts task-less, even when cloning a Device that's wired into a running Workflow.
- `positionX`/`positionY` are supplied by the caller in the request body, not derived server-side — see the two entry points below. Omitted entirely, they default to `null` (unplaced), same as a brand-new list-created Device.

**Devices list (15.7) — "Duplicate" row action**: a third icon button alongside Edit/Delete. Calls the duplicate endpoint with no position in the body. The new row appears on the table's next reload, sorted by name like any other row — no config screen opens automatically, since the clone is already exactly as configured as its source and ready to use or edit like any existing row.

### 15.10 Real heartbeats — `PUT /collectors/{collectorId}/heartbeat`, added 2026-08-31

Direct request from Luc, 2026-08-31: "when the heartbeat is enabled, send a specific heartbeat endpoint every half of the period (like is 120s, every 60s) using the datacollector API endpoint for the heartbeat." Supersedes the "this app never sends heartbeats" framing recorded throughout section 7.5, 15.8, and the top of section 15 — **for heartbeat only**. Still not built: pulling `GET /collectors` for reconciliation, and auto-re-registering when a heartbeat comes back `CONFIG_PENDING` — both flagged as natural follow-ups, not asked for here.

**Endpoint contract** (`datacollector-api-v3 (2) (2).yaml`'s generic `/collectors/{collectorId}/heartbeat` operation — not the Zebra-FX9600-specific example lower in the same file, which is a different, device-branded path): `PUT {gateway}/collectors/{collectorId}/heartbeat`, same `apikey` header auth as register/reads.

> **Live-verified 2026-09-01 — the spec's request body was wrong.** Probed against the sandbox tenant (`api.sandbox.bartender-tt.com`) with a really-registered collector: **the only accepted body field is `timestamp`** (ISO-8601). `configVersion` — and every other extra key tried (`config`, `version`, `status`, `collectorId`, `reportedAt`, `heartbeatAt`) — comes back `400 { error: { code: "VALIDATION_ERROR", field: "configVersion", message: "Unknown field." } }`. So `configVersion` is **not sent** (same category of spec-vs-reality gap as the `heartbeatConfig`-on-register object). Success: `200 { "status": "ONLINE", "lastSeenAt": "<ISO>" }`. A collectorId the platform never registered: `404 { error.code: "COLLECTOR_NOT_FOUND" }` — recorded as a heartbeat failure with the platform's own message. `CONFIG_PENDING` was never observed (with `configVersion` unavailable there's no client-side way to elicit it) — the client still recognizes it defensively in case the platform sets it server-side.

**Who gets a heartbeat, and how often**: a Device qualifies when `publishedAt != null` (a real registered platform Collector — heartbeating a Device Bartender doesn't know about is meaningless) **and** `heartbeatEnabled === true` (Bartender's own semantics: `false` means "always considered ONLINE," so sending would be pointless — matches Luc's literal "when the heartbeat is enabled"). Due when `now - lastHeartbeatSentAt >= heartbeatTimeoutSeconds / 2` seconds — Luc's own example, 120s period → every 60s. `lastHeartbeatSentAt` is stamped on every attempt, success or failure alike, so a persistently-unreachable tenant doesn't get hammered every tick — the same natural cadence either way, matching how a real reader just keeps sending on its own schedule regardless of whether the last one was acknowledged.

**Revised 2026-09-08 (BL-085, §13):** the `/2` is gone — `heartbeatTimeoutSeconds` is now the send interval directly (due when `now - lastHeartbeatSentAt >= heartbeatTimeoutSeconds`), and the default is 600, i.e. one heartbeat every 10 min instead of every 60s. Done to cut Neon compute after the free-tier outage. Existing rows were backfilled to 600.

**Revised again 2026-09-08 (§13, "heartbeatConfig / model" probe):** `heartbeatEnabled` / `heartbeatTimeoutSeconds` are **no longer internal-only** — the new sandbox `datacollector-api` version accepts a `heartbeatConfig: { enabled, timeoutSeconds }` on `POST /collectors/register` (closed schema, `timeoutSeconds` must be `> 0`, echoed by `GET /collectors/{id}`), so `buildCollectorRegistrationPayload` now sends it on every publish/resync (§15.8). The local heartbeat-tick send interval and the platform's `heartbeatConfig.timeoutSeconds` are the same stored number — the simulator pings on the same cadence it tells the platform to expect. The heartbeat *endpoint* itself is unchanged (`{ timestamp }` only). Same probe found `model` is now required on register — see §15.8.

**Immediate heartbeat on workflow start (2026-09-08).** Devices are `Offline` by default (BL-086, §15.3) and the platform only learns a Collector is alive from its heartbeat, not from the reads a run pushes it. So `PATCH /api/workflows/[id]` with `status: RUNNING` now fires one heartbeat per attached device (published + `heartbeatEnabled` + has a `collectorId`) via the shared `sendAndRecordHeartbeat` helper, in `waitUntil()` — best-effort, never blocks or fails the start. `lastHeartbeatSentAt` is stamped so the regular tick doesn't immediately re-send; the tick then keeps them alive every `heartbeatTimeoutSeconds` for the rest of the run (an `ACTIVE` device passes the tick's non-`OFFLINE` filter). Same pattern as BL-086's turn-online paths.

**Revised again 2026-09-08 (BL-086, §13):** the candidate filter already skipped `Offline` devices (via `getDeviceState`), and Devices are now `Offline` by default (§15.3) — so a Device only heartbeats inside a bounded Online window someone opened. `runHeartbeatTick()` also runs an **auto-offline sweep** at the top of every run: `updateMany({ where: { autoOfflineAt: { lte: now }, offlineAt: null }, data: { offlineAt: now, autoOfflineAt: null } })`, reverting expired windows so the fleet self-quiets. The send/record body was extracted to an exported `sendAndRecordHeartbeat(device, creds)` helper so the turn-on paths (§15.5a / §15.6) fire an immediate heartbeat through the identical code.

**Mechanism**: a new external-scheduler-driven route, `app/api/cron/heartbeat-tick`, same shape as the run engine's own `workflow-tick` (16.5) — `CRON_SECRET`-guarded (`x-cron-secret` header or `Authorization: Bearer`), GET and POST both accepted. **Kept as its own route, not folded into `workflow-tick`**: heartbeat health is a Device/publish concern (15.8), independent of whether any Workflow exists or is running at all — a Device can have heartbeat enabled with zero Workflows attached to it. This does mean Luc needs a **second** external per-minute scheduled call (cron-job.org or equivalent) pointed at the new route, alongside the one already hitting `workflow-tick` — a real, required manual step outside the codebase, flagged explicitly rather than assumed.

**Credentials**: **revised 2026-09-02 (bug fix, BL-074b)** — both cron ticks (this one and the run engine, BL-063) now resolve Bartender credentials **per resource owner** via `makeOwnerCredentialsCache()` (`lib/bartenderLocations.ts`), not a single global account. The old `getServiceCredentials()` picked the oldest connected user and used their tenant + key for *everyone's* devices/workflows — so once the app went multi-tenant, any Device on a different tenant got `COLLECTOR_NOT_FOUND` on every heartbeat, and any Workflow on a different tenant produced only empty batches (mint / `getStock` hit the wrong tenant). A published Device is registered on *its owner's* tenant (publish uses that user's key), so its heartbeat must go there; same for a Workflow's reads/mint. The cache resolves each owner at most once per tick. If an owner has no connection, that device/firing is marked failed ("the device owner has no Bartender connection configured") rather than silently sent to the wrong place.

**Result tracking** — three new `Device` columns: `lastHeartbeatSentAt` (`DateTime?`), `lastHeartbeatStatus` (`String?` — `"ONLINE" | "CONFIG_PENDING" | "FAILED"`), `lastHeartbeatError` (`String?`, cleared on the next success). Surfaced in the Device config modal as a small heartbeat-health line, same in-modal-banner treatment as the existing platform sync-health section (15.8) — kept out of the 4-state Device visualization (15.3) entirely, same reasoning as sync health: "a sync failure shows as an in-modal banner, not a 5th colour."

**A stale comment this feature makes wrong**: `components/DeviceConfigModal.tsx` currently filters registration-response reconciliation to `CONFLICT`/`BROKEN` only, with a comment reading "OFFLINE is expected — this app never sends heartbeats — and not surfaced." That assumption is exactly what this feature changes. The filtering behavior itself is still correct (`CONFLICT`/`BROKEN` are unrelated to heartbeats and should keep surfacing exactly as they do) — just the comment is now wrong and should be fixed. Whether Bartender-side `OFFLINE` reconciliation should start being surfaced now that heartbeats are real is a separate, undecided product question — flagged to Luc, not decided here either way.

**Built 2026-09-01 (BL-072 — v0.24.0).** Migration `add_device_heartbeat_tracking` (3 nullable columns). `lib/bartenderDataCollector.ts` `sendHeartbeat(tenantUrl, apiKey, collectorId)` — body `{ timestamp }` only (see the live-verified box above; the planned `configVersion` param was dropped). `lib/deviceHeartbeat.ts` `runHeartbeatTick()` — modeled on `runTick()`: selects `heartbeatEnabled && publishedAt != null && collectorId != null`, due when `now - lastHeartbeatSentAt >= heartbeatTimeoutSeconds/2`, optimistic `updateMany` claim on `lastHeartbeatSentAt` (concurrent-tick-safe), then `sendHeartbeat` → records `ONLINE` / `CONFIG_PENDING` / `FAILED` + `lastHeartbeatError` (cleared on success). `app/api/cron/heartbeat-tick/route.ts` — verbatim copy of `workflow-tick`'s auth/shape, reuses `CRON_SECRET`. `DeviceConfigModal` shows a heartbeat-health line off `syncSource` (`error-banner` when `lastHeartbeatError`, else a `.note` "Last heartbeat: ONLINE, <time>"); the stale `conflictOrBrokenMappings` comment is corrected (filtering unchanged). **E2E-verified against the sandbox**: auth 401/401/OK (header + bearer); ONLINE path (a really-registered collector → `lastHeartbeatStatus: "ONLINE"`, error cleared); FAILED path (`COLLECTOR_NOT_FOUND` recorded, sim unaffected); due-check fires at `timeout/2` and not before; 3 overlapping ticks → exactly one sends. **Still needs from Luc**: a second external per-minute scheduled call (cron-job.org or equivalent) pointed at `/api/cron/heartbeat-tick` with the same `CRON_SECRET` — the code alone doesn't self-schedule.

### 15.11 Manual feed — one-off send from a Ready Device (BL-078), added 2026-09-02

Resolves the deferral noted at the top of section 15 ("on verra ça plus tard"). Direct request from Luc: for a Device that's configured/published but **not currently in a running Workflow** — the **Ready** state (15.3), never Offline (that state's own "heartbeat and manual send are paused" wording stands, untouched by this feature) — let the user pick an Item Feed (16.1) and fire it once, on demand, through that Device. Three things asked for specifically: pick from the library of existing Item Feeds, duplicate one of them, or define a brand-new one inline, all from the same popup. Two entry points: clicking a **Ready** Device marker on the Overview map (15.6 — replaces the "Manual data send — coming soon" placeholder that's stood in for this since BL-046), and clicking anywhere on a Device's row on the Devices list (15.7) — **new**, that page's rows aren't click-targets today, only their discrete row-action icons are.

**Deliberately scoped as a standalone one-off, not a miniature Workflow run** — the single biggest judgment call in this design, called out explicitly because it determines what does and doesn't get built:

- **Reuses the run engine's own batch-resolution logic** (`resolveBatch()` in `lib/workflowRun.ts`, currently module-private — export it) so a manual `NEW` mints for real via Serialization API v3 exactly like an automated firing (same `MAX_NEW_ITEMS_PER_FIRING = 10` cap, no separate cap needed), a manual `PRESENT` queries real stock the same way, and a manual `FIXED` sends the same literal list. Nothing about *how a batch is resolved* is reinvented.
- **Does not fan out along Flow Links, and does not create an `InFlightBatch`.** A manual feed's items are read once, on the Channel the user picked, and the "journey" stops there — it does not simulate the item continuing on to whatever the Device's Task (if it has one) would otherwise route it to. Rationale: Luc's framing is explicitly about a Device "not in automated mode" — a manual send is meant to be an isolated, deliberate test action, not a way to inject one step into an otherwise-automated graph run. A Device that happens to be attached to a *stopped* Workflow (still Ready — 15.3) can be manually fed like any other Ready Device; its Task/Flow Links are simply not involved.
- **Does not write a `SimulatedRead` row.** `SimulatedRead.workflowId`/`taskId` are both required, non-nullable columns (16.5/16.6) — a manual feed usually has neither a Workflow nor a Task in play, so writing one would mean loosening that constraint (a real migration) for what is, by design, not a workflow-run event. Chosen instead: reuse the existing visibility this app already has for a real platform write — the manual feed's own real `POST /reads` call (when the Device is published and has a `collectorId`) is already captured by the endpoint-call log (`ApiCallLog`/`loggedFetch`, §19) and, once processed, shows up for real in the EPCIS-events tab (§7.9/§19) — both already-built surfaces, no new one needed. **Flagged consequence, not silently absorbed**: because there's no `SimulatedRead` row, items sent by a manual feed do **not** count toward the Overview "Items generated" KPI (14.4) or appear in any Workflow's own activity — only via the two real-platform-backed views above. If that gap turns out to matter to Luc once this is in front of him, the fix is a small follow-up (nullable `workflowId`/`taskId` on `SimulatedRead`, logged as a manual entry with both null) — deliberately not done in this first build to avoid an FK-relaxing migration for what's meant to be a lightweight feature.
- **Targets one of the Device's own Channels directly** (15.1's `channels` JSON array lives on `Device`, not on `Task`) — a Channel picker in the popup, pre-selected when there's only one (the common case, since every Device starts with exactly one auto-added Channel).
- **Item Feed picker is scoped to the caller's own feeds only** (`ownerId === session.user.id`, not `visibilityWhere`'s owned-or-shared) — mirrors §17.3's existing cross-owner composition rule for attaching an Item Feed to a Workflow's canvas ("only ever uses its own owner's... Item Feeds"), and the established pattern that a shared-to-you feed is brought into your own library by duplicating it from the Item Feeds list page first (16.9), not used cross-owner in place. Same reasoning extended here rather than inventing a new rule: **"Duplicate an existing feed" inside this popup means duplicating one of the caller's own already-listed feeds** (a quick variant before firing — e.g. a copy of a `NEW` feed with the quantity tweaked) via the existing `POST /api/item-feeds/[id]/duplicate` (16.9), not pulling in someone else's shared feed. **"Create a new one on the fly"** reuses the existing `ItemFeedForm` component inline (already built for the Item Feeds page and the Workflow canvas's own "+ New feed" tile, 16.4) — no new form to design.
- **Ownership gate matches every other mutating action in this app** (§17.2): manual-feed is owner-only on the Device, 403 for a shared-not-owned one — the map already routes a shared-not-owned Device to the read-only info panel regardless of state (BL-068/069), so this falls out for free there; the Devices list needs the same `readOnly` check applied to its new row-click.
- **`NEW`'s live-permanent-write warning** (16.1's existing per-kind info text) is shown inline when a `NEW` feed is selected, same text already written for the Item Feed creation dialog — no extra confirmation step added on top of it, so a manual send stays a single deliberate click rather than a click-then-confirm; revisit if Luc wants more friction here specifically given manual sends are by definition more frequent/ad-hoc than a scheduled tick.

**Devices list row-click, a second judgment call**: the list's rows have never been click-targets — only Edit/Offline-toggle/Duplicate/Delete icons are. Rather than making only Ready rows clickable (everything else inert), this mirrors the Overview map's existing per-state click routing (15.6) exactly, so every row behaves consistently regardless of state: **Pending** → config screen (15.4), **Ready** → this new manual-feed popup, **Active** → the existing read-only info panel, **Offline** → the existing offline-toggle popup. Flagged as the reasonable default rather than a literal restatement of what Luc asked (he only described the Ready case) — cheap to build since the map already has this exact routing table to copy, and avoids a list page where most rows do nothing when clicked.

**Not built here**: any change to the automated run engine, Flow Link fan-out, or `SimulatedRead`/`InFlightBatch` schema — this feature is additive, reusing `resolveBatch()` and the platform-push half of `emitReadAndScheduleHops()` (split out as its own exported helper so both paths share one implementation) without touching the automated path's own behavior at all.

## 16. Workflows — Item Feeds, Tasks, Flow Links (resolves BL-003)

Design discussed and confirmed with Luc 2026-08-30, still to be built. This is the real workflow engine BL-003 always deferred — a Workflow is a graph of Tasks (each attached to a Device) connected by Flow Links, simulating items physically moving from one read point to the next (dock door → sorting tabletop → storage shelves, branching by GTIN). Building screen: a node/edge graph editor, not a form.

### 16.1 Item Feed — reusable batch-of-items definition

A named, reusable entity, defined once (in a library, or inline from the canvas — see 16.4) and **placed** onto a Workflow canvas as its own node any number of times, across any Workflows (see 16.3 below — a Feed's *definition* is shared; each canvas placement is its own instance). Three kinds, picked at creation, each with its own creation-dialog shape **and its own explanatory info text describing what it actually does** — Luc's explicit ask, 2026-08-30, applies to all three kinds, not just `PRESENT`:

- **Common fields**: `name`.
- **`NEW`** — mints fresh EPCs via the Serialization API v3 (section 7.6, BL-073) every time this Feed fires. `quantityMin`/`quantityMax` (equal values = a fixed count, otherwise randomized per firing) and an `gs1Standard` picker are common to all 8 supported standards (**expanded 2026-09-17, BL-089** — see §7.6's "GS1 standard expansion" for the full per-standard contract): `sgtin-96` (default) / `sgtin-198` / `sscc-96` / `grai-96` / `giai-96` / `gid-96` / `dsgtin-plus` / `dsgtin-plus-plus`. Which *other* fields a Feed needs depends entirely on the chosen standard — the four GTIN-based ones (`sgtin-96`/`sgtin-198`/`dsgtin-plus`/`dsgtin-plus-plus`) keep **one or more GTINs** (revised 2026-08-30 — a Feed is no longer limited to a single GTIN; total spread across the listed GTINs per the allocation note below), while the four non-GTIN ones (`sscc-96`/`grai-96`/`giai-96`/`gid-96`) instead carry their own standard-specific identifier fields (company prefix + extension/asset-type/item-reference, or general-manager-number + object-class for `gid-96`, which has no company prefix at all) and show no GTIN picker. `dsgtin-plus`/`dsgtin-plus-plus` additionally carry the lot-code and shelf-life-period mechanism (§7.6) and, for `dsgtin-plus-plus` only, a required custom domain name. **Hard-capped at 10 items per firing in total, app-enforced, regardless of the configured `quantityMax`, for every standard** — Luc's explicit safety limit given each call is a real, permanent write to the live platform ("we get real serialized item from the platform... let's just allow not more than 10 new items at a time, we will level up the limit later when it is fully baked in"). No manual "generate now" escape hatch — it fires automatically like everything else, the cap is the safety net, not a human-in-the-loop step. Info text: explain plainly that this creates real, permanent items on the live Bartender tenant.
- **`PRESENT`** — carries a `locationCode` + `zoneCode` (a specific site+zone, since Zones aren't globally unique) and a product-match mode, **revised 2026-08-30 per Luc**: exactly **one** GTIN, **multiple** specific GTINs, or **all** ("only sends the GTIN[s] if some are present on the location/zone... or multiple or even all" — Luc's words) — `all` means match whatever's actually present in that zone, unrestricted by GTIN. At firing time, queries the Inventory API's `POST /stock/analytics` (§7.8, `dimensions: ["hexa", "product.pid"]`, BL-070) for the real EPCs of the matching GTIN(s) (or everything, if `all`) in that zone. **Quantity, revised 2026-09-03 (BL-070b) — no minimum, and a take-all default.** `PRESENT` has **no `quantityMin`** (you can't force more items than are present). A `presentTakeAll` flag (default `true`, "most of the time we want the full stock" — Luc) decides each firing: `true` pushes the entire current zone stock; `false` caps the firing at `quantityMax`, sampling a random subset of that size. Empty stock (or fewer than the cap) means fewer/zero items that firing — never an error, per Luc's original framing ("if none are present no items are scanned and send through the collector"). Info text: explain that this pulls from what's really recorded as present in that zone right now, and can come back empty.
- **`FIXED`** — a literal, explicit list of specific items (EPC hex or URN, user-entered) — confirmed 2026-08-30, not a recipe. Fires the exact same items every time; quantity fields and GTIN selection don't apply. Info text: explain that the same fixed items are (re-)sent every time this Feed fires, useful for repeatable test scenarios.

**Quantity-across-multiple-GTINs allocation, not yet specified by Luc**: when a `NEW`/`PRESENT` Feed lists more than one GTIN, how the target quantity is split across them isn't settled — default assumption for a first build: each individual unit in the batch is assigned a uniformly random GTIN from the Feed's list (or, for `PRESENT`, from whatever's actually present when `all` is selected), until the target quantity is reached. Flag to Luc once this is visible if a different allocation (even split, weighted, etc.) is wanted instead.

**Open runtime detail, still not settled**: whether a category search (section 7.7) is purely a *finder* that still resolves to concrete GTINs added to the list at creation time, or something that stays a live category reference — default assumption unchanged from the original design: it's a finder, the list of GTINs is what's actually stored.

### 16.2 Task — a Device doing work in a Workflow

A Task attaches one Device to one Workflow. **Revised 2026-09-04 (Luc): a Device can be a Task in several Workflows at once** — at most once per Workflow (`Task @@unique([workflowId, deviceId])`), but no longer removed from one to be used in another. The canvas device palette on any Workflow shows every published device the caller owns that isn't already on *that* canvas, regardless of use elsewhere. A Device is `ACTIVE` (15.3) while *any* of its Workflows is `RUNNING`. `Device.task` (1:1) became `Device.tasks` (1:many); `lib/deviceState.ts` reads `device.tasks.some(t => t.workflow?.status === "RUNNING")`. Each of that Device's Channels can receive input from any number of upstream connections — **revised 2026-08-30**: a Channel's inbound connections are no longer an exclusive single choice (Item Feed *or* Flow Link) — they're the union of however many **Feed Links** (16.3) and **Flow Links** (16.3) happen to target that Channel, matching Luc's explicit ask that a Device's input can be fed by multiple Feeds at once ("Those feed can be linked to inputs of devices, at any place so that I can have multiple feeds as input of a device"). A Channel with no inbound edges of either kind simply isn't fed.

The simulator does **not** track "where an item currently is" as its own concept — once an item's read event is generated, its Zone/status mapping is entirely the real Bartender platform's business (per the original framing: "this mapping is not defined here in the simulator, as we only simulate item flows"). What the simulator does track is the in-flight batches needed to actually run the graph — see 16.5.

### 16.3 Feed Node, Feed Link, and Flow Link — the graph's edges (and one more node type)

**Revised 2026-08-30**: Item Feeds get their own visual identity on the canvas, distinct from Task nodes — Luc's explicit ask: "I want the Item Feed to have their own box on the workflow diagram, different from the device, with a big Icon, background with navy blue color, text in white." Two graph concepts follow from that:

- **Feed Node** — a placement of a reusable Item Feed onto one specific Workflow canvas, at one specific position. The same Item Feed *definition* can be placed as **multiple separate Feed Nodes** — on the same canvas, or across different Workflows — each an independent instance with its own position, per Luc: "A same feed can be instantiated and use at multiple input position on a diagram." Placing a Feed Node doesn't require the Feed to already exist in a library first — the canvas palette supports defining a brand-new Item Feed inline (16.4).
- **Feed Link** — an edge from a Feed Node's output to a Task's Channel input. Carries its own `fireIntervalSeconds` (moved here from the old per-Channel-input model, since a Channel can now receive from several Feed Links, each potentially firing at its own cadence) — while the Workflow is `RUNNING`, this edge fires a fresh batch from its Feed every interval, unconditionally (no manual trigger, even for `NEW` — the 10-item cap in 16.1 is the safety net, not a human click). Any number of Feed Links can target the same Channel, and a Channel can simultaneously have both Feed Links and Flow Links feeding it — no exclusivity, no fan-in limit.
- **Flow Link** — an edge from one Task's output Channel to another Task's input Channel (unchanged from the original design). Carries a **delay range** (`delayMinSeconds`/`delayMaxSeconds`), an optional **filter** (GTIN list and/or category list), and an **else** flag — at most one outgoing edge per Task/Channel can be the catch-all that receives anything no other edge's filter claims. No fan-in limit here either — Luc confirmed "not limited, many upstream task to this one."

### 16.4 Canvas UI — graph editor, not a form

### 16.5 Run & automation engine

A Workflow's existing `RUNNING`/`STOPPED` status (15.2) becomes real: while `RUNNING`, the graph actually executes, continuously, server-side — **and keeps running even if no one is logged into the app** (Luc's explicit requirement). This can't be driven by anything in the browser (a tab-local timer dies when the tab closes) — it needs a server-side scheduler independent of any open session.

- **Firing cadence**: **revised 2026-08-30** — cadence lives on the **Feed Link** (16.3), not on the Channel itself, since a Channel can now have several Feed Links each firing independently; while its Workflow is `RUNNING`, each Feed Link fires a fresh batch from its Feed every `fireIntervalSeconds`, unconditionally (no manual trigger, even for `NEW` — the safety net is the 10-item cap in 16.1, not a human click).
- **In-flight batches**: a Feed Link firing creates a batch (the resolved list of items — minted, pulled, or the fixed list) sitting at its target Channel, immediately generating a **simulated read event** there (logged locally, **and — since BL-063, 2026-08-31 — also submitted for real via `POST /datacollector/reads`** while the Workflow is RUNNING; since BL-070, 2026-09-02, `PRESENT` batches push for real too — real EPCs pulled from `POST /inventory/stock/analytics`, see 7.5/7.8). The batch then evaluates that Task/Channel's outgoing Flow Links: for each edge whose filter matches (or the `else` edge, for anything unmatched), a copy of the batch is scheduled to arrive at the downstream Task's Channel after that edge's delay, generating another simulated read event on arrival, and the process repeats from there. A Task/Channel with no outgoing edges is a terminal point — the batch's simulated journey just ends.
- **Per-item GTIN routing (2026-08-31)**: batch resolution now records a GTIN *per item*, not one per batch — `NEW` gives each minted unit its own randomly-assigned GTIN, `PRESENT` in GTIN_LIST-of-one carries that GTIN, everything else is `null`. Flow Link fan-out is evaluated **item by item**: a single firing of a mixed-GTIN batch can split across several downstream Tasks, each Flow Link taking only the items whose own GTIN is in its `filterGtins` (the `else` link mops up the rest). `SimulatedRead` / `InFlightBatch` persist the `itemGtins` list plus a `gtin` summary column (migration `add_per_item_gtin`).
- **Safety auto-stop**: each Workflow gets a `maxRunDurationMinutes` setting — once a `RUNNING` Workflow has been running longer than that, the scheduler flips it back to `STOPPED` automatically; restarting it is a manual action in the UI, never automatic. Luc's explicit ask, to avoid an unattended Workflow (especially one with a `NEW` entry point writing real data) running forever if forgotten. **No default duration specified yet — flagged for Luc to set (or confirm a proposed default, e.g. a few hours) once this is being built**, and this — like the 10-item cap — is meant to be a conservative starting point, adjustable later, not a permanent ceiling.
- **Scheduler mechanism**: Vercel Cron is the natural fit given this app's existing hosting, calling a protected API route on a fixed schedule to process due firings and check auto-stop deadlines. **Needs a live check before being relied on**: Vercel's cron-frequency limits differ by plan (a plan limited to daily invocations would make per-Task interval firing unworkable) — confirm what Luc's actual Vercel plan/tier allows before building around it; if native Cron can't fire often enough, fall back to an external free scheduler (e.g. cron-job.org) hitting the same protected route every minute via a shared secret, same idea as `CRON_SECRET`-style protection.
- **Concurrency + retention (BL-081, 2026-09-04).** `runTick()`'s firing and arrivals loops process up to `TICK_CONCURRENCY = 6` items at once (`mapWithConcurrency()`) instead of one at a time — each due FeedLink/arrival is independent (different task/channel, and every DB claim is a per-row atomic `updateMany`), so this is safe and cuts a busy tick's wall-clock time (a workflow with many FeedLinks firing in lockstep, e.g. RTLS Stock's 30 zones every 10 minutes, used to serialize that many sequential Bartender round-trips inside one `maxDuration: 60` invocation). `makeOwnerCredentialsCache` and the per-tick in-stock-window cache both cache the in-flight Promise (not just the resolved value) so concurrent firings for the same owner/tenant share one lookup rather than each firing a redundant one. Separately: `InFlightBatch` rows are now deleted once processed (or fizzled) instead of left marked `processedAt` forever, and `SimulatedRead` is pruned inline to the latest 500/workflow after every write (same pattern as `ApiCallLog`) — neither table had any retention before this, and both were growing without bound.
- **Single combined endpoint (BL-084, 2026-09-08).** The run engine tick and the heartbeat tick (§15.10) were two separate `CRON_SECRET`-guarded routes, each hit by its own per-minute external job against both the prod and the staging branch — enough DB traffic to keep Neon's compute from ever auto-suspending, which exhausted the free-tier compute quota and took production down (see §13 2026-09-08). `/api/cron/tick` now runs both (`lib/cronTick.ts` `runCombinedTick()`, `Promise.allSettled`); `/api/cron/workflow-tick` and `/api/cron/heartbeat-tick` still work but are flagged `deprecated`. The external scheduler should point at the one `/api/cron/tick` and run it every ~minute.
- **Cron skip-gate (`lib/cronClock.ts`, 2026-09-08; store changed 2026-09-09).** The scheduler hits `/api/cron/tick` every ~minute so a `RUNNING` workflow keeps ~60s reactivity — but on Neon's Launch plan autosuspend can't drop below 5 min, so a per-minute *DB-touching* tick pins the compute 24/7 even when nothing runs (the same shape that caused the §13 outage). The gate lets an idle tick return **without any Prisma call**: the earliest instant the engine next has real work (`computeNextDueAt()` — min over every `RUNNING` workflow's FeedLink next-fire, pending `InFlightBatch` arrival, `maxRunDurationMinutes` deadline, due heartbeat, and BL-086 auto-offline sweep; `now + 30min` when nothing is scheduled) is kept as `nextDueAt` (epoch-ms) in **Upstash Redis** (Vercel Marketplace). *(Was a Vercel Global Config item until 2026-09-09 — Global Config's Hobby plan caps writes at 100/month and this key is rewritten every real tick, so it ran out; §13 2026-09-09. Upstash's free tier ~500K commands/month covers a per-minute read+write comfortably.)* A Redis REST read never touches Postgres, so while `nextDueAt` is in the future every tick is a single out-of-band read and the compute autosuspends; once it's in the past the full tick runs and rewrites `nextDueAt` from the state it left behind. The key is **per Vercel environment** (`cronclock:nextDueAt` for production, `cronclock:nextDueAt_preview` for staging) so one shared store doesn't have the two environments clobbering each other's clock, and it carries a **1-hour TTL** as a self-heal backstop (writer stops ⇒ key expires ⇒ next tick reads `null` ⇒ full tick ⇒ rewrite). `bustCronClock()` collapses `nextDueAt` to now from the mutations that create imminent work — a workflow flipped to `RUNNING` (§16.5 route), a device coming online (§15.5a/§15.6). **Fail-open**: needs the Upstash REST URL + write token in the environment (Vercel injects them when the integration is connected; `upstashCreds()` accepts `UPSTASH_REDIS_REST_URL`/`_TOKEN`, `KV_REST_API_URL`/`_TOKEN`, or any prefixed `*REST_API_URL`+`*REST_API_TOKEN` pair); missing either, or any read/write error, and the gate is inert — every tick runs in full, exactly as before. Only `/api/cron/tick` is gated; the deprecated split routes are not.

### 16.6 Data model implication — supersedes the placeholder Device↔Workflow link, and drops the old per-Channel "input type" field

Today's `Device.workflowId` (a direct FK, section 15.2's "minimal Workflow model... no creation/editing UI") is superseded by this design: a Device relates to a Workflow **through** a Task (`Device` 1:many `Task` since 2026-09-04, `Task` many-to-one `Workflow`), not directly. `lib/deviceState.ts`'s state derivation moves from `device.workflow?.status` to "is any of `device.tasks[].workflow` RUNNING" — same 4-state outcome, different path to it.

`Task.name` is an optional per-Task label override, **null by default** (was silently set to a snapshot of the Device's name at Task creation, 2026-09-04 fix — that snapshot is why a later Device rename didn't show on the canvas). The canvas shows `task.name || task.device.name`, so with `name` null it tracks the live Device name. Migration `device_multi_workflow` nulled every existing `Task.name` (no task-rename UI exists, so all values were just the stale copy).

**Revised 2026-08-30**: there is no separate `TaskChannelInput.inputType`/`itemFeedId` field anymore — a Channel's "is it fed, and by what" is derived purely from which edges (Feed Links, Flow Links) actually target it, not from a stored exclusive-choice field. `ItemFeed` (the reusable definition) is Workflow-agnostic and can be placed as a `FeedNode` on any Workflow's canvas any number of times; a `FeedLink` connects one `FeedNode` to one Task's Channel and carries its own `fireIntervalSeconds`.

Existing seed fixtures (2 Workflow fixtures, several Devices attached directly) get re-seeded as Tasks (plus a couple of Feed Nodes/Feed Links for realistic demo data) rather than migrated data-for-data, consistent with how earlier redesigns in this project (BL-042, BL-049) simply rewrote and re-ran the seed script rather than preserving fixture rows through a schema change.

### 16.9 Cloning an Item Feed — Duplicate (list) and Copy / Paste / Duplicate (canvas context menu), added 2026-08-31

Decided 2026-08-31, direct request from Luc: the same fast-cloning affordance built for Devices (15.9) applied to Item Feeds — the follow-up §17.3 flagged as "not built in this batch." Two entry points, sharing one server-side operation: the Item Feeds list (16.1's library view) and the Workflow canvas (16.4), right-clicking a Feed Node.

**Not to be confused with placing the same Feed again.** The canvas already has a distinct, pre-existing mechanism for reusing one Item Feed definition: dragging it from the palette onto the canvas creates a new **Feed Node** (16.3) that references the *same* `ItemFeed` id — no new `ItemFeed` row, and editing that definition later changes every placement of it at once (this is the "a same Feed can be instantiated at multiple input positions" behavior from 16.3). **Duplication is different**: it creates a **brand-new, independent `ItemFeed` row** — its own id, its own name, its own owner — that can be edited afterward without touching the original, exactly mirroring how Device duplication (15.9) creates an independent `Device` row rather than a second reference to the same one.

**What a clone copies vs. resets** — new `POST /api/item-feeds/[id]/duplicate`:

- Copied verbatim: `kind`, `gtins`, `categoryCode`, `presentMatchMode`, `presentTakeAll`, `quantityMin`, `quantityMax`, `locationCode`, `zoneCode`, `fixedItems` — the clone is exactly as configured as its source, whichever of the three kinds it is.
- `name` becomes `"{source.name} (Copy)"`, same convention as Device cloning, not de-duplicated further on repeat clones (accepted as-is, same reasoning as 15.9).
- `ownerId` is always the caller, `shared` always resets to `false` — regardless of the source's own owner/shared values. Matches §17.2's escape-hatch pattern: the visibility check on the source is `isOwner(source, userId) || source.shared` (not ownership), since cloning something shared-to-you is the intended way to bring a copy into your own workspace.
- No position field — unlike a Device, an `ItemFeed` definition has no `positionX`/`positionY` of its own (that lives on `FeedNode`, a separate row per canvas placement). The list entry point creates only the `ItemFeed` row. The canvas entry point additionally creates a `FeedNode` placing it — see below.

**Item Feeds list (16.1's library view) — "Duplicate" row action**: a third icon button alongside Edit/Delete, same treatment as the Devices list. Calls the duplicate endpoint; the new row appears on the table's next reload. **Disabled on a shared-not-owned row** — following the Devices list's actual built behavior (15.9/§17.4: "the list-page Duplicate button... is disabled on shared rows"), not the Overview map's. Nothing on the Item Feeds list plays the map's role of "the place cloning-from-shared is offered" — the canvas context menu (below) fills that role instead, since duplicating a feed only makes sense in the context of a Workflow you're placing it on.

**Workflow canvas — right-click on a Feed Node**: mirrors 15.9's map context menu (Copy / Paste / Duplicate, same `ContextMenu` component — see `CHARTE-GRAPHIQUE.md`'s note on generalizing it), wired via React Flow's `onNodeContextMenu`, and scoped to Feed Nodes only — right-clicking a Task node does nothing new here, since Device cloning already has its own two entry points (15.9).

- **Copy** — stores the right-clicked Feed Node's underlying `itemFeedId` in local component state (`feedClipboard`, scoped to `WorkflowEditor`, gone on page reload — same lifetime as the map's `deviceClipboard`). No server call.
- **Paste** — disabled while `feedClipboard` is empty. Clones the *clipboard* feed (not necessarily the node just right-clicked) and places the new `FeedNode` at the position the menu was opened at, converted to flow-space via `screenToFlowPosition` (the canvas's equivalent of the map's `clientToFloorPlanCoords`). Copying isn't consumed by pasting — the same clipboard entry can be pasted more than once.
- **Duplicate** — clones the right-clicked Feed Node's own feed directly, no clipboard involved, placed at a small fixed offset (+24/+24, already in flow-space — no coordinate conversion needed since the source node's own `position` is flow-space) from the source node.
- **Remove from workflow** (added 2026-08-31, v0.23.1) — a 4th, destructive row (separated, danger-styled). `DELETE /api/feed-nodes/[id]` — removes only this Feed Node placement and its feed links (`FeedLink.feedNode` is `onDelete: Cascade`); the shared `ItemFeed` definition stays in the library. A `confirm()` dialog spells that out ("The feed definition itself stays in your Item Feeds library."). The `ContextMenu` component gained an optional `onDelete?` + `deleteLabel?` — omitted at the Overview-map call site, so the marker menu still shows only Copy/Paste/Duplicate.

Paste and Duplicate are each a two-call sequence — `POST /api/item-feeds/[id]/duplicate` to create the new `ItemFeed`, then `POST /api/feed-nodes` to place it — followed by a reload of the canvas state, matching how every other canvas mutation already refreshes.

**Read-only gating is simpler here than on the Overview map.** The map gates Copy/Paste/Duplicate per-marker (a device can be individually shared while others on the same map aren't). A Workflow canvas has no equivalent — §17.3's same-owner composition rule already guarantees every Feed Node's underlying `ItemFeed` shares its parent Workflow's `ownerId`, so there's no such thing as an individually-shared Feed Node inside an otherwise-owned canvas. The whole-canvas `readOnly` flag (§17.2/§17.4's build note: "gates every mutation entry point") is therefore the only gate this menu needs — it doesn't open at all (or the browser's own default menu is left alone) when the open Workflow is shared-not-owned, consistent with the palette being hidden and every other mutation entry point being inert in that state.

**Component reuse**: `components/DeviceContextMenu.tsx` is already fully generic (`x`, `y`, `canPaste`, `onCopy`, `onPaste`, `onDuplicate`, `onClose` — nothing Device-specific in its props). Renamed to `components/ContextMenu.tsx` (component `ContextMenu`) as part of this work, with `LocationMapCard.tsx`'s one existing import updated to match — one component, two call sites, rather than a near-duplicate.

**Built 2026-08-31 (BL-071 — v0.23.0; "Remove from workflow" row — v0.23.1).** Implemented exactly as specced above. `app/api/item-feeds/[id]/duplicate/route.ts` mirrors the Device route (visibility-only source check `isOwner || shared`; `ownerId` = caller, `shared` = false always; Json fields spread `...(x !== null ? {...} : {})`; no request body). Item Feeds list: `DuplicateIcon` + `handleDuplicate`, a 3rd `row-icon-btn-ghost` between Edit and Delete, `disabled` on shared-not-owned rows. `components/DeviceContextMenu.tsx` → `components/ContextMenu.tsx` (`git mv`; component renamed; props untouched apart from the later optional `onDelete?`/`deleteLabel?`). `WorkflowEditor.tsx`: `feedClipboard` / `feedContextMenu` state, `duplicateFeedNode` + `deleteFeedNode` helpers, `onNodeContextMenu` on `<ReactFlow>` (`if (readOnly || node.type !== "feed") return; e.preventDefault()`). E2E-verified in the browser: menu opens at cursor with Copy / Paste / Duplicate / — / **Remove from workflow** (red); Duplicate + Copy→Paste each create an independent `ItemFeed` + `FeedNode`; "Remove from workflow" → confirm → the Feed Node and its 1 feed link are gone, the 4 `ItemFeed` rows are untouched; right-click never also opens the edit modal.

### 16.10 GS1 standard expansion — `ItemFeed` fields and form design (BL-089, added 2026-09-17)

The full API contract (per-standard `input` fields, the DSGTIN lot/date mechanism, filter defaults, what's deliberately out of scope) is documented once in §7.6's "GS1 standard expansion" subsection — this section covers the `ItemFeed` data-model and `ItemFeedForm.tsx` design that surfaces it, so the contract isn't duplicated here.

**Reconciled 2026-09-17 (Cowork) against Claude Code's live-testing pass** (§7.6's "Live-testing findings vs. the spec above" — read that subsection first). Two corrections below versus the design as first written earlier the same day: the custom-domain field is gone (§7.6 explains why), and DSGTIN's lot code now has a genuine third "none" state, since a live mint with no `lotCode` at all was confirmed to work. The GTIN/SKU-null EPCIS gap on `demotrackandtrace` doesn't change any field below — see §7.6's decision (ship + document, don't hold the feature back for a tenant-side gap).

**New `ItemFeed` columns, all nullable, all `NEW`-kind-only** (mirrors how `gs1Standard` already works — populated only for the standard actually in use, `null` otherwise):

| Column | Used by | Notes |
|---|---|---|
| `companyPrefix` | `sscc-96`, `grai-96`, `giai-96` | 6–12 digits, validated in `buildItemFeedData`. **No `companyPrefixLength`** for any of the 4 non-GTIN standards — live-confirmed (§7.6): all three worked without it, despite a separately-uploaded newer copy of the spec claiming SSCC-96 needs one. |
| `extensionDigit` | `sscc-96` | single digit string, defaults to `"0"` |
| `assetType` | `grai-96` | free text |
| `itemReference` | `giai-96` | free text — UI label "Individual asset reference" |
| `generalManagerNumber` | `gid-96` | free text |
| `objectClass` | `gid-96` | free text |
| `gs1Filter` | every standard except `FIXED`/`PRESENT` | int 0–7, pre-filled per standard (§7.6), always editable |
| `gs1LotMode` | `dsgtin-plus`, `dsgtin-plus-plus` | `"AUTO"` (default) \| `"FIXED"` \| `"NONE"` — **`"NONE"` added 2026-09-17**, live-confirmed a mint with no `lotCode` field at all succeeds (§7.6) |
| `gs1LotCode` | `dsgtin-plus`, `dsgtin-plus-plus`, `gs1LotMode = "FIXED"` only | ≤20 chars, user-entered or "Suggest"-generated once |
| `gs1DateField` | `dsgtin-plus`, `dsgtin-plus-plus` | `"expirationDate"` \| `"bestBeforeDate"` |
| `gs1ShelfLifeDays` | `dsgtin-plus`, `dsgtin-plus-plus` | whole number of days; the form's own number+unit input converts to this on save |

`~~gs1CustomDomainName~~` — **removed, corrected 2026-09-17.** The original design (written from the spec doc alone) assumed `dsgtin-plus-plus` needed a dedicated custom-domain field inside `input`/`context`. Claude Code's live test proved that wrong: a real `dsgtin-plus-plus` mint succeeded with no such field at all, using only the request's existing top-level `digitalLinkBaseUrl` (the same field already in this app's vocabulary for Digital Link generation), and returned a fully-formed `digitalLink`. So there's no new "domain" concept to add — `dsgtin-plus-plus`'s domain-in-EPC-binary requirement (per the spec's own framing, "embedded custom domain name" is that standard's distinguishing feature) is satisfied by sending the same `digitalLinkBaseUrl` this app would use for any Digital Link output, just always sent (not only when the `digitalLink` format is requested) because for this one standard it also affects the `hex` encoding. `gs1DigitalLinkBaseUrl` — a single URL field, shown and sent **only for `dsgtin-plus-plus`** (not `dsgtin-plus`, which doesn't embed a domain in its binary at all per §7.6's format table) — defaults to `https://id.gs1.org` (the platform's own documented default) when left blank, editable if Luc wants a different resolver domain.

`gs1Standard` itself is unchanged in shape (`String?` on `ItemFeed`, already existed) — just widened from the 2-value `null | "sgtin-198"` set to all 8 standard ids, with `null`/anything unrecognized still normalizing to `"sgtin-96"`.

**Form design (`components/ItemFeedForm.tsx`)** — the existing NEW-kind block (`gs1Standard` select, GTIN picker, quantity min/max) gets a further conditional layer keyed on `gs1Standard`:

- The **identifier-format `<select>`** grows from 2 options to 8, grouped for readability (optgroups or just ordered clearly): GTIN-based first (SGTIN-96 default, SGTIN-198, DS-SGTIN+, DS-SGTIN++), then non-GTIN (SSCC-96, GRAI-96, GIAI-96, GID-96) — each option's existing one-line help text pattern (already used per-kind, §16.1) extended per standard, e.g. "SSCC-96 — logistic units (pallets, cases). No GTIN; identified by a company prefix instead." **DSGTIN's two options each carry an extra line**: "Note: on the current Track & Trace platform version (T&T 12.6), items minted this way don't resolve a GTIN in the platform's own EPCIS/inventory records — a downstream `PRESENT` feed or Flow Link GTIN filter may not recognize them. Expected to be fixed in T&T 12.7. See CLAUDE-CONCEPT.md §7.6." (the decision made 2026-09-17: ship with this documented rather than hold the standard back, now confirmed as a temporary, version-bound platform limitation — see §7.6).
- **GTIN picker (`ProductPicker`) shown only for the 4 GTIN-based standards** — hidden entirely for `sscc-96`/`grai-96`/`giai-96`/`gid-96`, replaced by that standard's own small field group (company prefix + one more field, or general-manager-number + object-class for `gid-96` — see the table above). Switching `gs1Standard` between a GTIN and a non-GTIN standard clears whichever set of fields no longer applies, mirroring how switching `kind` already resets kind-specific fields today.
- **`gs1Filter`** — one small number input (0–7), shown for every `NEW` standard, pre-filled from the recommended-defaults table (§7.6) the moment `gs1Standard` changes (only if the user hasn't already typed a value — don't clobber an edit in progress), with a one-line note that it's editable and what it recommends for this standard. `gid-96`'s default (0) carries its own extra note that the value is unconfirmed for this standard.
- **DSGTIN-only block**, shown only when `gs1Standard` is `dsgtin-plus` or `dsgtin-plus-plus`:
  - Date type: a small toggle (same `icon-toggle` pattern already used for `PRESENT`'s match-mode toggle) — "Expiration date" / "Best-before date".
  - Shelf-life period: a number input + a days/weeks/months unit `<select>`, converted to `gs1ShelfLifeDays` on save; a note states plainly that the actual date is computed fresh every time the feed fires (today + this period), not fixed when the feed is saved.

## 17. Per-user workspaces — ownership & admin-controlled sharing, added 2026-08-31

Decided 2026-08-31, direct request from Luc flagging a real gap in everything built so far: Devices (section 15), Workflows and everything that hangs off one — Task, FeedNode, FeedLink, FlowLink (section 16) — and Item Feeds have had **zero ownership tracking** since they were first built. Every logged-in user has always seen, and been able to edit, the exact same shared pool — confirmed by inspecting every `findMany` in `app/api/devices`, `app/api/workflows`, `app/api/item-feeds`: none of them filter by user at all. One piece of this was already correct and needs no change — see 17.6.

### 17.1 Ownership model

`ownerId` (required, FK to `User`, `onDelete: Cascade`) and `shared` (`Boolean`, default `false`) are added directly to the three "root" entities Luc named — `Device`, `Workflow`, `ItemFeed`. `Task`, `FeedNode`, `FeedLink`, `FlowLink` do **not** get their own `ownerId` — each already hangs off exactly one `Workflow` via `workflowId`, so ownership/sharing is inherited transitively from `workflow.ownerId`/`workflow.shared` rather than duplicated onto four more tables. (`Task` also references a `Device` directly — see 17.3.) Every create route sets `ownerId: session.user.id` server-side, unconditionally — never accepted as a client-supplied field.

### 17.2 Visibility & edit rules

- **List/GET-many** (`GET /api/devices`, `/api/workflows`, `/api/item-feeds`, and `GET /api/tasks`/`/api/feed-nodes`/`/api/feed-links`/`/api/flow-links` filtered by `workflowId`): `where: { OR: [{ ownerId: session.user.id }, { shared: true }] }` on the root entity (or via its parent Workflow for the four child tables).
- **GET-one**: same visibility test — 404 (not 403, to avoid confirming a record exists at all) if neither owned nor shared.
- **Any mutating action** — PATCH, DELETE, Publish, Run/Stop, the Duplicate endpoint, everything: requires `ownerId === session.user.id` on the root entity (or its parent Workflow), full stop. A shared record is genuinely **read-only** to everyone except its owner — 403 on every mutating route for a non-owner, even though they can see it because it's shared.
- **This applies exactly as much to an ADMIN as to a plain USER in the app's normal, everyday UI** — explicitly confirmed with Luc, not assumed; see 17.4 for the one deliberate, narrow exception.

### 17.3 Cross-owner composition — a Workflow only ever uses its own owner's Devices and Item Feeds

A `Task` attaches one `Device` to one `Workflow`; a `FeedNode` places one `ItemFeed` onto one `Workflow`'s canvas. **Decided for v1**: both are only allowed when the Device/ItemFeed being attached has the **same `ownerId`** as the Workflow — never across owners, even when the Device/ItemFeed is `shared`. Sharing grants visibility and read-only use of the thing itself (17.2), not the right to wire it into someone else's Workflow — mixing ownership inside one Workflow's graph would make "your workflow, your devices, your feeds" (Luc's own framing) stop being true the moment anything is shared. `POST /api/tasks` and `POST /api/feed-nodes` both gain this check (403, distinct message, if the owners don't match), on top of each side's own ownership/visibility check.

If a user wants to use another user's shared Device or Item Feed inside their own Workflow, the fix is to **clone it into their own workspace first** — Device already has a Duplicate action (`BACKLOG.md` BL-065/066, `CLAUDE-CONCEPT.md` section 15.9); Item Feed gets the equivalent in section 16.9 (`BACKLOG.md` BL-071). This keeps the composition model simple (no partially-shared graphs) at the cost of an extra clone step; revisit if that friction turns out to matter in practice.

### 17.4 Sharing is an admin-exclusive action, and is deliberately *not* the same thing as admin visibility

Two explicit, separately-confirmed decisions from Luc that read like they pull in opposite directions, reconciled here:

1. **Only an ADMIN can flip a resource's `shared` flag** — not even the resource's own owner can self-serve sharing. The route that toggles it checks `session.user.role === "ADMIN"`, independent of who owns the record being shared.
2. **Admins get no blanket visibility into other users' workspaces in the app's normal, everyday UI** — the Devices list, Workflows list, Item Feeds list, Overview map, and Workflow canvas apply the exact same `ownerId === me OR shared === true` filter for an ADMIN as for a USER (17.2). There is no "admin sees every Device" mode on those pages.

Taken together: (1) needs a way for an admin to find and select a resource they don't otherwise see anywhere in the app, and (2) says the normal pages can't be that way. **Resolution**: a new, dedicated admin-only screen — **"Shared resources"** — is the *one* place in the app where an ADMIN's query genuinely lists every Device/Workflow/Item Feed across every user (grouped or filterable by owner), each row showing only enough to identify it (type/name, owner) plus a Share/Unshare toggle. Nowhere else grants that cross-user view, and this screen itself doesn't let an admin open or edit the underlying Device config or Workflow canvas — it's a sharing-management console, not a general oversight tool. Natural home: a new tab alongside the existing admin-only Users tab in Settings (section 4), since that's already the one place in the nav gated to `ADMIN`.

**Built 2026-08-31 (BL-068/069, Part 2 of 2 — v0.22.0).**

### 17.7 Hiding a shared resource from your own view (BL-079), added 2026-09-03

Direct request from Luc: a user should be able to permanently remove a shared Device, Item Feed, or Workflow from their own screen. This is distinct from everything else in section 17 so far — §17.4's admin-only `shared` toggle is a global on/off for *everyone*; this is a **per-user, self-service** preference that never touches the resource's own `shared` flag or affects any other user's view of it.

**"Permanent" — confirmed with Luc rather than assumed**, since it changes what has to be built: it means *durable across sessions* (not a client-side/session-only dismiss that comes back on next login), **not** a one-way dead end with no recovery. A user who hides something by mistake, or later wants it back, can restore it themselves from a new **Settings → Hidden items** tab (see below) — this is the reconciliation of "permanent" (it really does leave every list/map/canvas until they say otherwise) with not being a foot-gun.

**Scope**: only ever applies to a resource that's **shared and not owned** by the caller. An owner already has Delete for their own Devices/Item Feeds/Workflows (15.7/16.1's list/18.9's list) — hiding your own would be a different feature (something closer to archiving) that Luc didn't ask for and isn't built here. Attempting to hide a resource you own, or one that isn't visible to you at all (not owned, not shared), 404s — same "don't confirm a record exists" posture as every other visibility check in this section (§17.2).

**Data model** — three small per-type tables rather than one polymorphic table, matching this app's existing preference for explicit typed relations over a loose string reference (Task/FeedNode/FeedLink/FlowLink all do this; contrast `Device.locationCode`, which is a plain string precisely *because* Locations aren't a local model at all — that precedent doesn't generalize here, Device/Workflow/ItemFeed **are** local models with real ids):

```prisma
model HiddenDevice {
  id        String   @id @default(cuid())
  userId    String
  user      User     @relation(fields: [userId], references: [id], onDelete: Cascade)
  deviceId  String
  device    Device   @relation(fields: [deviceId], references: [id], onDelete: Cascade)
  createdAt DateTime @default(now())
  @@unique([userId, deviceId])
}
// HiddenWorkflow / HiddenItemFeed — identical shape, workflowId/Workflow and itemFeedId/ItemFeed respectively.
```

Real FKs with `onDelete: Cascade` on both sides means a hidden-row cleans itself up automatically if either the user or the underlying resource is later deleted — no orphan cleanup job needed. Each of `User`/`Device`/`Workflow`/`ItemFeed` gains the matching back-relation (`hiddenBy` on the resource side is the one that matters for the visibility filter below; name it consistently across all three so the filter reads the same shape everywhere).

**Visibility filter** — `visibilityWhere()` (`lib/ownership.ts`, §17.2) gains one more condition, but only on the *shared* branch; an owned row is never affected by anything hidden, since hiding your own isn't a thing (above):

```ts
{ OR: [
  { ownerId: userId },
  { shared: true, hiddenBy: { none: { userId } } },
] }
```

A hidden row's `HiddenDevice`/etc. entry is **not** cleared by the admin toggling `shared` off and back on later — the user's own dismissal is a separate, sticky preference that an unrelated global re-share shouldn't silently undo. It only goes away when the user explicitly restores it (or the resource/user is deleted, per the cascade above).

**Where the action lives**: the hide affordance is added only to the three list pages — Devices (15.7), Item Feeds (16.1's library view), Workflows (16.1's list) — each already renders a `SharedBadge` and a disabled Delete on shared-not-owned rows (BL-068/069); a new row-action icon takes the logically-equivalent "remove it" slot for those rows specifically. **Deliberately not added to the Overview map or the Workflow canvas** — once a resource is hidden it's excluded at the query level everywhere (the map/canvas fetch through the same `visibilityWhere`), so there's nothing left to wire on those surfaces; this mirrors the existing "one canonical place per action" pattern already established for cloning-from-shared (§17.4's built note: the map, not the list, is where Device cloning-from-shared happens — here it's the reverse surface, the list, for the reverse action). Confirms with a short dialog before hiding ("Remove this shared Device from your view? You'll still be able to bring it back from Settings → Hidden items.") since it's a durable action, even though it's also reversible.

**Settings → Hidden items** (new tab, `SettingsTabs.tsx`) — **not** admin-gated, shown to every user (contrast the existing ADMIN-only "Shared resources" tab, §17.4, which manages the global `shared` flag). Lists everything the caller has personally hidden across all three types — same visual shape as `SharedResourcesTable.tsx` (type chip, name, owner) but a **Restore** action instead of a share toggle, and scoped to `userId = session.user.id` rather than cross-owner. Empty state when nothing's hidden.

**Not built here**: any admin visibility into who has hidden what (this is a personal preference, not something Luc asked to audit), and no change to the admin Shared-resources screen itself (§17.4) — hiding and the `shared` flag are two independent, non-interacting mechanisms by design.

**Built 2026-09-04 (BL-079 — v0.32.0).** Migration `add_hidden_resources` (`HiddenDevice`/`HiddenWorkflow`/`HiddenItemFeed`, cascade FKs both sides, `@@unique([userId, <resource>Id])`; `hiddenBy` back-relation on each resource). **One `visibilityWhere` was enough** — the `{ shared: true, hiddenBy: { none: { userId } } }` literal type-checks for all three `WhereInput`s and the nested `workflow:` filters, so no per-model split. `lib/hiddenResources.ts` `hideResource`/`unhideResource(kind, userId, id)` — hide gate is a raw "exists ∧ `shared` ∧ not owned" check (deliberately not `visibilityWhere`, so a repeat hide is a no-op, not a 404), `upsert` on the unique key; unhide is an ungated idempotent `deleteMany` (restoring always allowed, even after the admin un-shared it). `POST`/`DELETE` routes at `/api/{devices,workflows,item-feeds}/[id]/hide` (POST hides, DELETE restores). `GET /api/hidden-resources` — every logged-in user, own hides only. `components/HideFromViewButton.tsx` — eye-slash row action that *replaces* the already-disabled Delete on shared-not-owned rows of the three list pages (prompt said "add a button"; replacing the inert one reads cleaner), confirm + optimistic removal. `components/HiddenResourcesTable.tsx` + a non-admin **Hidden items** tab in Settings (after Bartender Connection), Restore per row. Round-trip verified for all three types with a synthetic second user: hide removes it from every `visibilityWhere` surface, owner's view untouched, own-hide/unshared-hide 404, double-hide no-op, hide survives an admin `shared` off→on, Restore brings it back.
